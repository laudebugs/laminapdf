# CLAUDE.md

Guidance for Claude Code (and humans) working in this repository.

## What Lamina PDF is

Lamina PDF is a platform for anything and everything PDF: creating PDFs from code, parsing and extracting content, rendering, editing, form filling, signing, and transforming documents. The first core crates (`laminapdf-syntax` and `laminapdf-cos`, ported from the pdf-basics spike, `laminapdf-model`, `laminapdf-ops`, `laminapdf-save`, `laminapdf-content`, `laminapdf-text` and `laminapdf-build`) and the `laminapdf` façade over them exist, with its WASM bindings (`laminapdf-wasm`, built into the `@laminapdf/wasm` package), the TypeScript API over them (`@laminapdf/sdk`) and the `laminapdf` command-line tool (`laminapdf-cli`), and two sites: the docs site (`apps/docs`) and the website (`apps/site`). Decisions are recorded as ADRs in `docs/decisions/`; accepted so far: a Rust core, `MIT OR Apache-2.0`, bytes in / bytes out with no AGPL/GPL dependencies ([0001](docs/decisions/0001-core-language-and-licence.md)); wasm-bindgen + tsify bindings ([0002](docs/decisions/0002-binding-strategy.md)); the Cargo + pnpm + `cargo xtask` monorepo, npm packages under `@laminapdf` (amended 2026-10-31) ([0015](docs/decisions/0015-monorepo-layout-and-tooling.md)); one lockstep version for every crate, `@laminapdf/wasm`, `@laminapdf/sdk` and the render packages (`@laminapdf/render`, `-hayro`, `-pdfium`) and `@laminapdf/viewer`, driven by Changesets and copied into Cargo by `cargo xtask version sync`, `0.x` with `-alpha.N` pre-releases until `0.2.0` (amended 2026-11-11: the alphas end, and `0.x` follows SemVer), `v<version>` tags and a release lane that publishes on `v*` tags: crates.io trusted publishing, npm trusted publishing; amended 2026-11-05: a daily release cut and tagged by a release bot after the nightly passes, npm trusted publishing from a GitHub-hosted runner with no approval step, `docs.laminapdf.com` from each release and `next.docs.laminapdf.com` from `main` ([0017](docs/decisions/0017-versioning-and-release.md)); cargo-deny and licence hygiene ([0019](docs/decisions/0019-supply-chain-and-licence-hygiene.md)); the reader tolerance policy and `Limits` ([0003](docs/decisions/0003-reader-tolerance-and-limits.md)); the document model ([0005](docs/decisions/0005-document-model.md); generation strategy §6: our own builder over `laminapdf-cos` reusing `pdf-writer`/`subsetter`/`skrifa`/HarfRust, per the `krilla-fit` spike, accepted when its PR merges); the op log and undo ([0006](docs/decisions/0006-op-log-and-undo.md)); the save planner ([0007](docs/decisions/0007-save-planner.md)); the test strategy ([0018](docs/decisions/0018-test-strategy.md)); content-stream reading ([0023](docs/decisions/0023-content-stream-reading.md)); content-stream editing: `ContentOps`, operators keeping their source bytes grouped into objects with their graphics state and glyphs, identity by owner, ordinal and source hash (`content-object-stale`), an encoder that copies unchanged spans into new streams, copy on write for shared streams and forms, tagging kept through edits, text runs by MCID then extraction's lines, fonts reused, subset again or substituted, every edit labelled ([0022](docs/decisions/0022-content-stream-editing.md)); the error and diagnostic contract, `LaminaPdfError` in TS ([0026](docs/decisions/0026-error-and-diagnostic-contract.md)); coordinates in top-left points of the displayed CropBox, raw user space only in `UserSpace…` types, 0-based page `index` ([0027](docs/decisions/0027-coordinates-units-and-page-indexing.md)); the façade rules, the lock in the binding edge (core stays `Send + !Sync`), `Job::step(Budget)` in work units and `CancelToken` ([0028](docs/decisions/0028-facade-rules-jobs-and-cancellation.md)); mobile bindings: UniFFI `=0.32.2`, a `crates/lamina-ffi` edge crate, hand-written Swift/Kotlin layers that cancel async calls through a Rust token, SwiftPM and Maven Central AARs, 16 KB pages, `mobile-release` and size budgets ([0029](docs/decisions/0029-mobile-bindings-and-packaging.md)); the CLI and MCP contract: one `laminapdf` binary over a command library, verb-first grammar, qpdf page ranges with pdftk handles, `-` for stdin and stdout, exit codes 0–5, versioned JSON with committed schemas, errors on stderr, read-only MCP with required roots ([0031](docs/decisions/0031-cli-and-mcp-contract.md)); the extraction output `laminapdf.extract/1`: blocks in reading order with top-left boxes, structure tree then XY-Cut++, hidden text never in text, models only as licence-checked plug-ins ([0030](docs/decisions/0030-extraction-output-and-model-plugins.md)); for the web reader: the `RenderBackend` trait (bounded RGBA tiles, never model data from the renderer), PDFium by default on every viewer surface (pinned and SHA-256 checked) with hayro as the CI oracle and measured switch criteria, MuPDF prohibited, the two-parsers rule ([0004](docs/decisions/0004-render-backend.md)); React 19 chrome around a framework-free `@laminapdf/viewer`, one document worker per document, a typed RPC extending `@laminapdf/sdk/worker`, transferred `ImageBitmap`s, single-threaded with no COOP/COEP in v0.1 ([0009](docs/decisions/0009-web-client-architecture.md)); one `Platform` interface with capability flags and no platform checks in UI code ([0010](docs/decisions/0010-platform-adapter.md)); static-assets Workers on Cloudflare (the website at `laminapdf.com`, the reader at `app.laminapdf.com` with staging at `staging-app.` and production only from `web-v*` tags; amended 2026-11-05), documents never through our servers (`#url=` fragment), ten testable privacy guarantees, strict headers, opt-in-only telemetry and hosted features ([0011](docs/decisions/0011-cloudflare-topology-and-privacy.md)); the app shell UX: a docked inverted-L layout, registered modes that each own one secondary toolbar, one command registry behind the palette, toolbars, menus and shortcut help (every command with a visible home besides the palette), selection surfaces chosen by pointer (no floating toolbar on touch), page appearance separate from the UI theme, the phone shell, and `--paper-` tokens in primitive → semantic → component layers ([0024](docs/decisions/0024-app-shell-ux.md)); flowing layout as our own engine in `laminapdf-build` over `Surface` (Typst measured and rejected by the `flow-layout` spike), greedy pagination with keep rules, page templates, tagged by default, Markdown and `laminapdf.document/1` with JSON Pointer templates, `laminapdf build` and its MCP tool ([0032](docs/decisions/0032-flowing-layout-and-document-inputs.md)). The plan for the rest is in `docs/plans/architecture.md`, with the shareable libraries (contracts, CLI/MCP, AI extraction, agent docs, mobile; Rounds L1–L6; ADRs 0029, 0030 and 0031 accepted) in `docs/plans/shareable-libraries.md`, and the work that the Hacker News research (`docs/research/hacker-news/`) found users lack (published proof, checks for what files hide, extraction users can check, flowing layout; Round T; ADR 0032) in `docs/plans/trust-and-proof.md`, and the reader as a browser extension for Chrome, Edge, Firefox and Safari (Round K, a nice-to-have that starts after the web reader's launch; research in `docs/research/browser-extension/`) in `docs/plans/browser-extension.md`; don't assume decisions that aren't in an ADR.

Daily releases: `release-train.yml` runs after a full successful nightly on `main`. It prepares and atomically pushes a version branch and tag with the release bot. ## Working agreements

- **Always work in a git worktree.** Start every piece of work in a new worktree off main (see docs/guidelines/git-workflow.md). The repo is a bare clone; worktrees are folders inside it: `git worktree add -b <type>/<desc> <type>-<desc> main`. Never `git stash` across worktrees; remove the worktree after merge.
- **Work from the todo board.** Every PR implements one todo from [`docs/todos/`](docs/todos/README.md) (`ready/` → `ongoing/` → `done/`), except bot, CI-maintenance, typo, board-only and progress-snapshot refresh PRs, and bug fixes recorded in `docs/bugs/` ([bug triage](docs/guidelines/bug-triage.md)). Pick one from `ready/` whose dependencies are all `done/` (`cargo xtask todos` lists them); claim it by opening its work PR at once; its first commit moves it to `ongoing/` with `[skip ci]` in the message, so CI first runs on the work's first push. Merge with your own `--body`; otherwise the claim's `[skip ci]` lands on `main` and skips `main`'s workflows. The open PR is the claim, so check `gh pr list` before picking. Move it to `done/` in the same PR before merge, updating links and running `cargo xtask todos`. Plans link to their todos. See [git workflow §2](docs/guidelines/git-workflow.md#pick-work-from-the-todo-board).
- **Pull requests only.** `main` was initialized directly; every change since goes through a branch + PR. Branch names: `<type>/<short-description>` (e.g. `docs/pdf-research`).
- **Review every PR with `/code-review`, then merge.** After opening a PR, run `/code-review high <PR#>` (trivial PRs: `low`) without `--comment`: don't post review comments. Fix the findings in new commits whose messages list each finding and its fix. If there were more than 6 findings, run `/code-review low <PR#>` after the fixes and record those the same way. A non-trivial PR that adds or changes prose people read also gets `/writing-review`, whose findings are counted and fixed separately ([§7](docs/guidelines/git-workflow.md#7-review-and-merge-process)). Run `cargo xtask ci` locally, then squash-merge once CI is green. See [review and merge process](docs/guidelines/git-workflow.md#7-review-and-merge-process).
- **Check visual changes in a browser, from the user's side.** Try every change to what a user sees or touches on screen (the reader, the viewer, the sites, the components) in the built app in a real browser, as a person uses it (mouse, keyboard, real files). Judge it by what they can see and do; tests that only call an API don't prove it. Other changes need their own tests, not a browser. See [bug triage §7](docs/guidelines/bug-triage.md#7-prove-the-fix).
- **Never patch code just to make a test pass.** When a test fails, in CI or locally, find out why. Fix the product if it is wrong. If the test checks something that doesn't make sense, adjust it or remove it, and say why in the commit message. See [bug triage §6](docs/guidelines/bug-triage.md#6-fix-the-cause-not-the-symptom).
- **Conventional Commits** for commit messages: `type(scope): summary`.
- **Name the session after its PRs** with the `session-name` skill: `Yanny - [D2d:#421, E1c:#440]`.
- **Document as you go.** Plans go in `docs/plans/`, decisions in `docs/decisions/`, research in `docs/research/`. Update the folder's `README.md` index whenever you add a file.
- **Cite sources.** PDF behavior claims should point to ISO 32000-2 (PDF 2.0) or another primary source. Clearly label recommendations and opinions.
- **Spec first.** When implementing PDF features, read the relevant research chapter in `docs/research/` and the spec section before writing code. Real-world PDFs are frequently malformed — parsers must be tolerant, writers must be strict.
- **Use the project's skills.** Load the `/rust-best-practices` skill before writing or reviewing any Rust code, and the `/tauri-v2` skill before any Tauri work (`apps/desktop`, `src-tauri`, `tauri.conf.json`, commands, IPC, capabilities, the updater, bundling). Load `/writing` before drafting prose people read, and run `/writing-review` on it once the PR is open; [git workflow §7](docs/guidelines/git-workflow.md#7-review-and-merge-process) says which prose and how to handle the findings. Tell subagents to load these skills too. Where a skill and the guidelines in `docs/guidelines/` disagree, the guidelines win: note it in the commit message, and if the skill's rule is better, change the guideline in its own PR.
- **Mind licenses.** Many PDF libraries are AGPL or dual-licensed (e.g. iText, MuPDF/PyMuPDF). Don't add a dependency without checking its license.

## Code organization

Conventions that hold whatever the architecture ADRs decide (crate/package names in them are examples):

- [`docs/guidelines/code-organization.md`](docs/guidelines/code-organization.md): layout (`crates/laminapdf-*`, `packages/` as `@laminapdf/*`, `apps/`, `fixtures/`, `tools/xtask`, `spikes/` outside every workspace), dependency direction (pure bytes-in/bytes-out core, platform code only at the edges), public API, tests, when to split.
- [`docs/guidelines/rust.md`](docs/guidelines/rust.md): edition 2024, workspace `[lints]`, no `unwrap`/`expect`/`panic`/indexing in libraries, `unsafe` only in edge crates with `// SAFETY:`, `thiserror` errors.
- [`docs/guidelines/typescript.md`](docs/guidelines/typescript.md): strict tsconfig, ESM-only, no Node-only APIs in shared packages, named exports only, Biome, Vitest.
- [`docs/guidelines/maintainability.md`](docs/guidelines/maintainability.md): one home per concept (search before writing a helper), size budgets that only go down, one public path per item, no test code in shipped code, comments that say why.
- [`docs/guidelines/docs-writing.md`](docs/guidelines/docs-writing.md) and [`docs/guidelines/examples.md`](docs/guidelines/examples.md): reader-facing docs tell a story in plain English, with no internal IDs; examples use only the public API, carry no test scaffolding and read like code we would merge.

Hangs are caught by nextest's per-test timeout in `.config/nextest.toml` (robustness tests: 30 s), not by wall-clock asserts (ADR 0018); plain `cargo test` runs the same tests without the timeout.

CI has two required PR lanes ([ADR 0018 §2](docs/decisions/0018-test-strategy.md#2-ci-lanes)). Native Rust checks run on standard GitHub-hosted Linux, macOS and Windows, each on x64 and Arm64; macOS x64 only on pushes to `main` and in the nightly (`rust-macos-x64`, X9a), since its runners queue longest. Every leg that runs blocks `fast-gate`. The full lane's `gate` requires the Linux Arm64 Rust/TypeScript check, the whole `cargo xtask check` on Windows x64 (`check-windows`, X6), and the differential, fuzz and PDF suites. Every other job runs on Ubuntu x64; macOS Arm64 only where a Mac is needed (WebKit, the render goldens, the CLI's macOS build). Docs-only PRs skip the suites, while `changes` still runs docs checks, and other PRs skip each group of jobs their paths can't affect (`render`, `rust`, `ts`; CI caching plan §8.1). The desktop build and e2e legs also skip on a PR when its own runs or `main` already passed them on the same inputs (`desktop-key`, X10b), and CodeQL analyses only the languages a PR changes (X10c). All runners are fresh VMs; Rust and pnpm caches save only on pushes to main (pull requests, schedules and dispatches only restore them), and jobs that build the same thing share one Rust cache (`shared-key` `rust`, `wasm` or `xtask`, saved by one job; the nightly and release lanes save none). The compile cache (`.github/actions/rust-compile-cache`, X8a; [CI caching plan](docs/plans/ci-caching.md)) adds sccache over a Cloudflare R2 bucket after a job's toolchain step: pushes to `main` write it from the `rust-compile-cache` environment, everything else only reads it, and the release, deploy and nightly workflows never use it (`tools/xtask/src/workflows/compile_cache.rs`). Its trial runs it on the fast lane's Linux x64, macOS x64 and macOS Arm64 Rust legs, those marked `compile-cache: true` in the `changes` job's list of legs. No active workflow uses a self-hosted runner or its heartbeat. See [hosted runners and the public transition](docs/public-readiness.md).

The release lane (`.github/workflows/release.yml`, ADR 0017 §6, ADR 0018 §2) runs on `v*` tags and on `workflow_dispatch` (`gh workflow run release.yml --ref <ref> [-f ref=<tag-or-sha>]`; a dispatched `ref` must be an existing `v<version>` tag or a full commit SHA on `main`, checked before any checkout, since every job runs that ref's code on main's caches): `guard` (`cargo xtask release-guard`: refuses unless the latest full nightly run on `main` succeeded on the release commit or an ancestor: a scheduled run, or a dispatch with every input at its default, which nightly.yml's `run-name` titles "Nightly (full budgets)"; other dispatches don't count (ADR 0018 §2); `version check-tag`), then the fast lane (`check`, `wasm` with publint/attw, `size`), the full lane's suites, `@laminapdf/sdk` in every runtime, the nightly lane (`nightly.yml` via `workflow_call` with `record: false`: nothing recorded, no issue;
