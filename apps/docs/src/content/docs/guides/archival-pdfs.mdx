This guide builds PDF/A documents, which you need when a file must stay readable and look the same for decades: contracts, records kept by law, e-invoices. lamina writes PDF/A as it generates a document; it doesn't convert existing files to PDF/A.

## What PDF/A asks for

PDF/A is the archival subset of PDF. A PDF/A file carries everything it needs to be displayed: its fonts are embedded, its colours are defined, and nothing depends on the viewer, the network or a password. lamina writes three PDF/A profiles:

- **PDF/A-2b** ("basic"): the document looks the same everywhere.
- **PDF/A-2u** ("Unicode"): PDF/A-2b, and every glyph maps to Unicode, so the text can be searched and copied.
- **PDF/A-3b:** PDF/A-2b that may carry attached files of any kind.

Choose one with the `profiles` option (`BuildOptions::with_profile` in Rust). The builder then writes two things the standard asks for. It writes the PDF/A identification in the document's XMP metadata, the XML packet in the file that describes it. That packet always agrees with the Info dictionary, the older list of the same facts (title, author, dates) that PDF readers also show.

It also writes an output intent: a declaration of what device colours mean. The intent embeds an ICC profile, the standard file format that describes a colour space. lamina's output intent is sRGB, so RGB and gray colour are defined. `DeviceCMYK` is CMYK colour given as plain numbers, with no profile to say which inks they mean (`Color::cmyk` in Rust, four numbers in TypeScript), so the sRGB intent leaves it undefined.

`finish()` fails with a coded error for each rule the document breaks:

| Rule | Error |
| --- | --- |
| Every font is embedded (no standard 14 font) | [`font-not-embedded`](/reference/codes/font-not-embedded/) |
| No `DeviceCMYK` colour or CMYK image (the output intent is sRGB) | [`device-color-without-output-intent`](/reference/codes/device-color-without-output-intent/) |
| PDF/A-2u: every glyph maps to Unicode | [`glyph-without-unicode`](/reference/codes/glyph-without-unicode/) |
| PDF/A-2b, PDF/A-2u: no attached files | [`embedded-file-forbidden`](/reference/codes/embedded-file-forbidden/) |
| Every attached file has a MIME type | [`embedded-file-without-mime-type`](/reference/codes/embedded-file-without-mime-type/) |
| The PDF version is 1.7 or lower | [`profile-version-conflict`](/reference/codes/profile-version-conflict/) |

For CMYK colour under PDF/A, give the colour an ICC profile instead (`Color::icc` in Rust): an ICC-based colour defines itself. Transparency is allowed in PDF/A-2 and PDF/A-3.

## Attaching files: a hybrid invoice

PDF/A-3 lets a document carry other files, provided each one is associated with the document and says how it relates to it: its source, the data it was made from, or another representation of the same content. E-invoicing formats such as Factur-X and ZUGFeRD use this to put the machine-readable invoice (XML) inside the human-readable one (PDF).

`attach(name, bytes, mime, { relationship })` adds a file, its MIME type and its relationship, and lists it in the document's attachments. The example uses a made-up XML schema; a real e-invoice follows the EN 16931 standard and adds its own XMP metadata.

## How lamina checks its own output

Every example on this site that claims a PDF/A profile is validated each night with veraPDF, the open-source PDF/A and PDF/UA validator the PDF Association backs.

:::note[Details]
PDF/A is ISO 19005: PDF/A-2 is part 2 and PDF/A-3 part 3. Both build on PDF 1.7, as PDF/UA-1 does, which is why a PDF 2.0 document can't claim them.
:::
