## Context

The spike's strongest finding was about method: shared fixtures, byte-identical goldens, a corpus whose facts came from an independent tool (pypdf), and a differential fuzz (the same ~4,300 mutated files through two readers) caught bugs that single-implementation tests missed ([research ch. 07 §4](../research/pdf/07-spike-rust-and-typescript.md#4-what-we-learned)). The architecture research proposes four CI lanes, differential testing against pdf.js, PDFium, qpdf and pypdf, cargo-fuzz in the OSS-Fuzz layout and veraPDF ([report: repository](../research/architecture/app-and-package-architecture.md#the-repository-is-cargo-pnpm-and-a-task-runner-released-through-oidc-and-gated-by-a-pdf-corpus)). The parser guidelines ask for continuous fuzzing from day one ([ch. 04 §11.3](../research/pdf/04-interactive-security.md#113-guidelines-for-building-a-safe-parser-lamina)).

PR #8 also taught a lesson: a 1,000-page wall-clock test failed about half the time on a loaded machine in a debug build. It became a deterministic check plus an `#[ignore]`d release-mode scaling test (`crates/laminapdf-cos/tests/reader_cache.rs`).

The test layout rules (unit tests in-file, integration tests on the public API, `fixtures/` by path, goldens never rewritten by a test) are in [code organization §6](../guidelines/code-organization.md#6-tests-and-fixtures); fixture licensing is [ADR 0019](0019-supply-chain-and-licence-hygiene.md).

## Decision

### 1. Tiers

1. **Unit.** `#[cfg(test)] mod tests` in the same file; colocated `*.test.ts`. Fast, no fixtures beyond inline bytes.
2. **Integration.** `crates/*/tests/`, public API only, one file per topic, helpers in `tests/common/`. Read shared inputs from `fixtures/` by path. Random inputs use a fixed seed (the existing `tests/common` `Rng`) and print it on failure.
3. **Golden, byte-identical.** Expected outputs in `fixtures/golden/`. Every writer test that has a golden also runs twice and compares ([ADR 0001](0001-core-language-and-licence.md) determinism). Goldens change only through **`cargo xtask golden --update`** (added in B2; it regenerates every golden from its source and prints the list), and the diff is reviewed like code. A test never writes a golden.
4. **Corpus facts.** `fixtures/corpus/expected.json` holds facts extracted by independent tools, never by lamina: pypdf today (page count, revisions, xref kind, root keys, …), qpdf `--json` and pdf.js added as facts need them. A file where lamina deliberately differs is listed in an exceptions file with the [ADR 0003](0003-reader-tolerance-and-limits.md) rule that explains it.
5. **Property tests.** proptest for invariants: object serialise → parse is identity; for every op, apply then undo leaves the overlay as it was ([ADR 0006](0006-op-log-and-undo.md)); every saved document reopens with the same facts.
6. **Differential.** lamina against **pdf.js, PDFium, qpdf and pypdf** (MuPDF is excluded by [ADR 0001](0001-core-language-and-licence.md)): open/repair/fail outcome and page count first, then outline, text and round-trip as features land. Two sources: the large external corpus (nightly) and spike-style mutants of `fixtures/corpus` (a fixed-seed set of 500 in the full lane, compared with expectations precomputed by `cargo xtask differential --update`; the full set nightly with live tools).
7. **Round-trip.** Open → op → save → reopen in lamina, pdf.js, PDFium and `qpdf --check` (from B3).
8. **Render goldens** (Round C). PNGs per page rendered by PDFium and hayro, compared with perceptual thresholds; updated only by `cargo xtask render-golden --update`.
9. **Fuzzing.** cargo-fuzz targets in `fuzz/` with the layout OSS-Fuzz expects for Rust (`fuzz/Cargo.toml`, `fuzz/fuzz_targets/<name>.rs`), outside the main workspace like `spikes/` because it needs nightly Rust. Targets from B2: `lex`, `parse_object`, `flate_decode`, `open` (open and drive every read path, as `tests/common::exercise` does), `page_tree`; later `content` (B9), `ops_json` and `save_roundtrip` (B3), `extract_text` (B9c). Invariants: no panic, no hang (`-timeout=10`), memory under `-rss_limit_mb=2048`, and default [`Limits`](0003-reader-tolerance-and-limits.md) respected. Seeds come from `fixtures/`. Every crash becomes a minimised file in `fixtures/regressions/` and a named regression test. Apply to OSS-Fuzz once the repository is public.
10. **Conformance.** veraPDF (Docker image, external process only per [ADR 0019](0019-supply-chain-and-licence-hygiene.md)) over every generated example nightly; from B8 any violation fails.
11. **Performance and scaling.** Release mode only, in `benches/` or `#[ignore]` tests, run nightly. Scaling tests assert ratios that separate linear from quadratic growth (`pages_should_scale_linearly_with_shared_resources`: 4× the pages must take under 9× the time), never absolute durations. Benchmark history is kept; a regression over 10% opens an issue rather than failing the build.

**No wall-clock assertions in the PR lanes.** Hangs are caught by the runner's timeout (nextest `slow-timeout` with `terminate-after`), not by asserting elapsed time. The 30 s budget asserted in `crates/laminapdf-cos/tests/robustness.rs` moves to nextest configuration in B2.

### 2. CI lanes

| Lane | When | Runs | Budget |
| --- | --- | --- | --- |
| **Fast** | Every PR and push to `main` (exists, `.github/workflows/ci.yml`) | fmt, clippy `-D warnings` (native + wasm32), portability, tiers 1–5, doc tests, wasm build and size budget, TS checks, cargo-deny and npm licences, MSRV | ~10 min |
| **Full** | Every PR and push to `main` (added in B2); a required check. Runs its suites only when the change touches `crates/`, `packages/`, `apps/`, `fixtures/`, `fuzz/`, `tools/` or `Cargo.lock`, otherwise passes in seconds | Fast lane on Linux, macOS and Windows; the 500-mutant differential set; each fuzz target for 2 min; round-trip with qpdf; render goldens and Playwright from Round C | ~30 min |
| **Nightly** | Scheduled on `main` | Differential against live pdf.js, PDFium, qpdf and pypdf over the external corpus and all mutants; fuzz 10 min per target; veraPDF; hayro vs PDFium render diffs; perf and scaling | hours |
| **Release** | Tags (`.github/workflows/release.yml`, B7b; [ADR 0017 §6](0017-versioning-and-release.md#6-the-release-lane)) | Full + nightly suites on the release commit (the nightly suites skipped for a version-only commit on top of a nightly-passed one; amended 2026-11-05), packaging checks (publint, attw), clean-install smoke tests in each runtime (`cargo xtask verify-install`); refused unless the latest full nightly on `main` (scheduled, or dispatched with every input at its default; amended 2026-11-02) passed on the release commit or an ancestor (`cargo xtask release-guard`) | hours |

The Full lane is never skipped by a workflow-level `paths` filter: GitHub keeps a required check whose workflow didn't run as "Expected — waiting", which would block docs-only PRs. Instead the workflow always runs; a first job computes the changed paths (`git diff --name-only` against the merge base) and a final gate job, the one marked required, succeeds when the suites passed or were not needed. Pushes to `main` always run everything.

A nightly failure opens an issue automatically and blocks the next release, not unrelated PRs.

**Implementation note (X4, full lane).** [`.github/workflows/full.yml`](../../.github/workflows/full.yml) implements the Full row as follows:

- **The filter is inverted.** Instead of listing the code paths above, `cargo xtask changes` (run by the `changes` job against the merge base with the PR's base branch, renames counted as both paths) calls a PR **docs-only** when every changed path is on a short allowlist: `docs/**`, Markdown and `LICENSE*` files at the repository root, `.github/ISSUE_TEMPLATE/**` and `.github/PULL_REQUEST_TEMPLATE.md`. Everything else is code: root config nobody listed (`.cargo/config.toml`, `.gitattributes`, `rust-toolchain.toml`, `.github/actions/**`, workflows, lockfiles, a new root file), and Markdown outside those places, which can be a build input (a crate README used as its rustdoc and doc tests, a docs site's pages). The allowlist is defined once, in `is_docs` in `tools/xtask/src/changes.rs`, with unit tests for every pattern.
- **The gate.** `changes` outputs `code`, exactly `true` or `false` (pushes to `main` are always `true`). Each suite runs under `if: ${{ !cancelled() && needs.changes.outputs.code == 'true' }}`. The `gate` job (`if: always()`) fails when `changes` didn't succeed or `code` is anything else, when any suite failed or was cancelled, or when a suite was skipped on a code change; it is the only check branch protection needs from this workflow. A new suite uses the same condition and joins `gate`'s `needs`. The workflow also runs on `edited`, so retargeting a PR to another base re-classifies it.
- **Operating systems.** Native Rust checks (`cargo xtask check rust`) run on six standard hosted images: Ubuntu 24.04 x64 and Arm64, macOS 15 Intel and Arm64, Windows 2025 x64 and Windows 11 Arm64. Every matrix leg blocks `fast-gate`. The full lane also runs Rust and TypeScript checks on hosted Ubuntu Arm64; every other job uses Ubuntu x64, and hosted macOS Arm64 runs only what needs a Mac: WebKit, the render goldens and the nightly render diff (measured on macOS), and the CLI's macOS build. No workflow uses the former private Macs or Linux container, and Linux no longer has an availability switch. [Hosted runner notes and public transition](../public-readiness.md) record the image labels and setup. The full lane's `check-windows` ([X6](../todos/done/X6-windows-ci.md)) runs the whole `cargo xtask check` on hosted Windows 2025 x64, docs and TypeScript included, on every code PR, and `gate` requires it.
- **Differential.** `cargo xtask differential --full` checks 36 mutants per corpus file (504 for today's 14 files) from their own seed (`FULL_SEED` and `FULL_PER_FILE` in `crates/laminapdf-model/tests/common/mutants.rs`) against `fixtures/differential/full.json`, under nextest so a hang is killed. A file's mutants don't depend on the other corpus files, so adding one adds only its own. The exceptions are in `full-exceptions.toml`, grouped by cause (`files` lists), each still naming its ADR 0003 rule; a pair listed twice, an empty list or an entry for a file outside the set fails the test. The fast set (four mutants per file) is unchanged.
- **Fuzz.** `cargo xtask fuzz --all --time <N> --jobs 2` builds every target once, then fuzzes them two at a time in separate cargo-fuzz processes (per-input timeout 10 s × jobs, so CPU sharing isn't reported as a timeout crash; 2048 MB per process), and reports each failure as a crash (new crash inputs saved) or a build/setup problem. PRs run each target for 30 s, not the 2 min of the table above: a smoke test that keeps the PR lane near 6 minutes instead of 20; pushes to `main` keep 2 min (`--time 120`), so the corpus they save keeps growing, and the nightly lane keeps 10 min. Runs start from the corpus last saved on `main`; only pushes to `main` save it, minimised with `cargo xtask fuzz cmin`.
- **Capability matrix** ([X2](../todos/done/X2-capability-matrix.md)). The `suites` job runs `cargo xtask capabilities --check`: every test tagged `/// capability: <ID> <surface> <status>` with `cargo test`, failing when one fails or when [`docs/capabilities/README.md`](../capabilities/README.md) differs from what they prove. `cargo xtask check docs` (so every PR, docs-only ones included) checks the manifest against the feature inventory and rejects a README that differs from what the manifest and the tags generate. Core `write` and `round-trip` claims are accepted only on tests in `laminapdf-save/tests/roundtrip_suite.rs`, so tier 7's qpdf, pdf.js and PDFium checks back them.
- **Path portability.** Docs-only PRs skip native suites, so `cargo xtask check docs` (the full lane's `changes` job, every PR) rejects tracked paths Windows or a case-insensitive file system can't check out.
- **Docs-only PRs.** The fast lane classifies the PR the same way and skips its Rust, WASM, runtime, MSRV-and-spike and TypeScript jobs when it is docs-only; the full lane's `changes` job runs `cargo xtask check docs` (links, todo board, path portability) on every PR, so those checks still count toward `gate`.
- **Retries** (amended 2026-11-10). Rust tests never retry in the PR lanes: both set `NEXTEST_PROFILE=ci`, with `retries = 0` and the same slow-timeouts as the default profile. Browser suites retry a failed test once, and the shared setup actions' downloads retry up to three times (§4).
- **The fast lane's gate** ([X7](../todos/done/X7-fast-lane-gate.md), 2026-11-01). `gate` used to be the only required check, so a red fast-lane job didn't block a merge: B8b (#143) merged with the fast lane's rustdoc step failing and turned `main` red. `ci.yml` now ends with `fast-gate`, built like `gate`: it needs every other job of the fast lane and fails unless each one passed, or was skipped on a docs-only PR. Branch protection requires both. A test in `tools/xtask/src/workflows.rs` fails when a job of either lane is missing from its gate's `needs`.
- **Fewer, larger jobs** (2026-11-01). A code PR started 23 jobs over both lanes, so with several PRs open at once jobs waited up to 17 minutes for a runner, and most short jobs spent longer setting up than testing. The lanes now run 12, after three merges. The full lane's differential, capability matrix, round-trip and examples suites run one after another in one `suites` job with one build directory. The fast lane's MSRV check and the pdf-basics spike share a job. The full lane's five `@laminapdf/sdk` runtimes joined the fast lane's three, as two jobs (browsers; Deno, Bun, workerd and Node 22 and 26) over the `wasm` job's build, so the full lane no longer builds the same packages a second time. Jobs also do less. The fast lane's Rust job leaves the docs checks to the full lane's `changes` job on PRs. Each macOS job that installed pnpm used to download its store (290 MB) from the Actions cache, since pnpm kept it in the job's temp dir; `.github/actions/node-pnpm` keeps it in the runner's tool cache instead. `cargo xtask size` measures the modules on parallel threads.
- **The compile cache** (2026-11-12). Jobs that build Rust may compile through sccache over a bucket on Cloudflare R2, set up by [`.github/actions/rust-compile-cache`](../../.github/actions/rust-compile-cache/README.md) after the toolchain step, beside the Rust cache ([CI caching plan](../plans/ci-caching.md)). Only a push to `main` writes to it, with a token held in the `rust-compile-cache` environment, which only `main` may use; pull requests read it with a read-only token, and forks build without it. The release lane (`release.yml`, `cli-release.yml`, `release-train.yml`), the deploys (`web-deploy.yml`, `web-release-train.yml`, `docs.yml`, `site.yml`) and the nightly lane (`nightly.yml`, which the release guard trusts and the release lane calls) never use it, through any workflow or action they call, so an entry that is wrong or planted can't reach users or let a release through; `tools/xtask/src/workflows/compile_cache.rs` checks it. The trial on the Linux x64 and macOS x64 Rust legs ([X8a](../todos/ongoing/X8a-rust-compile-cache-trial.md)) decides whether the other Rust jobs take it ([X8b](../todos/ready/X8b-rust-compile-cache-everywhere.md)).
- **Timing** (measured on PR #30): `changes` about 20 s on a cold cache, so a docs-only `gate` finishes in under a minute after the job starts; a code PR's full lane took 18 minutes, fuzzing 13 of them.

### 3. Corpora: licensing and provenance

- `fixtures/` holds small files we may redistribute, each listed in `fixtures/README.md` with origin, licence and what it exercises ([ADR 0019](0019-supply-chain-and-licence-hygiene.md)). Generated and mutated files are ours (`MIT OR Apache-2.0`). Nothing with personal data.
- Large external corpora (pdf.js, PDFium and qpdf test suites, SafeDocs, veraPDF and Arlington test files) stay out of git: `cargo xtask corpus fetch` downloads them into a gitignored folder, pinned by SHA-256 in a manifest that also records each source's licence. CI caches them; the R2-hosted copy (report) is a mirror, not a source of truth.
- A corpus file that a licence forbids redistributing is never committed, even minimised; regressions from it are re-created synthetically.

### 4. Flaky tests

A flaky test is a bug. Within a day of noticing it, mark it `#[ignore = "flaky: #<issue>"]` (or `it.skip` with the issue) and assign the issue; fix or delete it within two weeks. PR lanes never retry Rust tests (nextest `retries = 0`). The nightly lane may retry them once only to *report* flakiness, and a test that passes on retry is still reported. Tests must not depend on time, ordering, the network or unseeded randomness. One exception on ordering: the desktop end-to-end suite shares one app per run, because its WebdriverIO service starts the app once, so its spec files run in a fixed order. Only the first, the empty state, needs its place; each other spec opens its own file and needs nothing an earlier one left ([ADR 0008 §8](0008-desktop-shell.md#8-test-strategy-per-os)).

Retries report, never hide (amended 2026-11-10). Real browsers on shared runners stall, crash and lose races that a test can't control: in the first three days on hosted runners, a pinch-zoom gesture in WebKit, a window title in all three engines and a status line in Firefox each failed three runs that passed when rerun. So the browser suites (the Vitest browser projects and the reader's and docs' e2e suites) retry a failed test once. `@laminapdf/test-utils/flaky` holds the one setting every suite spreads in. Each test that passed only on its retry gets a warning annotation, a line under "Flaky Tests" in the job summary (Vitest's own GitHub reporter) and `flaky=true` in its step's outputs, from which the nightly opens or updates its issue. The retry buys a day, not a pass: the rule above still applies. A browser page that crashes fails its whole file, which no retry repeats: it stays a failure and gets its issue.

Setup retries hide nothing of ours. The shared setup actions' downloads (`pnpm install`, Playwright's Chromium and system libraries, the WebKitGTK packages) run under `nick-fields/retry`, up to three times, each retry a warning. They download from registries and mirrors and test nothing, so a second try can only turn a network hiccup into a pass. apt runs as root, which the retry can't kill, so each apt call ends itself under `sudo timeout` (docs/bugs/ci-apt-retry-kill-eperm). `.github/actions/apt-fail-fast` makes a try fail sooner than that timeout. Each apt download gets 30 s and 3 tries, and its `update.sh` ends the try at once when an Ubuntu index can't be fetched (apt itself only warns). A third-party source the runner image lists still only warns: failing on it would fail every Linux job while it is down.

### 5. Shared expectations across languages

Fixtures, `expected.json`, error and warning codes (`fixtures/codes.json`, [ADR 0003](0003-reader-tolerance-and-limits.md)) and op samples (`fixtures/ops/`, [ADR 0006](0006-op-log-and-undo.md)) are read by the Rust tests and, from B6, by the TypeScript tests, so the bindings can't drift.

## Consequences

- PR feedback stays fast and deterministic; the expensive and environment-sensitive work runs nightly where a failure doesn't block unrelated work.
- External tools (pdf.js, PDFium, qpdf, pypdf, veraPDF) are needed only in full and nightly lanes; contributors don't need them for the fast lane.
- Goldens, differential expectations and render goldens each have one explicit update command; reviewers see every change.
- Maintaining the corpus manifest, the exceptions file and the fuzz regressions is ongoing work.
- Performance regressions are seen within a day, not at the PR that caused them.

## Alternatives considered

- **Wall-clock budgets in PR tests.** Flaky on shared runners (PR #8); ratios in release mode measure the same thing reliably.
- **Snapshot tools for PDF bytes** (`insta`). Fine for text, but PDF goldens need byte review and a regenerate step tied to their source.
- **Expected facts produced by lamina.** Circular: a bug would confirm itself.
- **Differential against external tools in every PR.** Slow and installs four toolchains; the precomputed mutant set catches most regressions.
- **Committing the large corpora.** Licences forbid it for much of them, and the repository would grow by gigabytes.
- **Retrying flaky tests automatically.** Rejected at first because it hides real races. Amended 2026-11-10: browser suites retry once, but a pass on the retry is reported and needs its issue, so the race stays in sight; Rust tests in the PR lanes still never retry. Rerunning a whole failed job by hand cost more and reported nothing.

## Implementation notes

### Nightly lane (X3a, 2026-10-29)

- **Workflow.** [`.github/workflows/nightly.yml`](../../.github/workflows/nightly.yml) runs on a cron on `main`, on `workflow_dispatch` and on `workflow_call`, so the release lane (B7b) can run the same suites. Its inputs are the fuzz seconds, the differential sample and `force-failure`. It replaced B2c's `fuzz.yml`. Each job is a `cargo xtask` task, and `cargo xtask nightly [--quick]` runs them all locally. A failed or timed-out job, a scaling test that passes only on retry, or a flaky link opens or comments on the issue "Nightly lane failing on <ref>" (label `nightly`). The benchmarks run after every job that doesn't depend on them, so they don't share the runners' Mac with those (2026-11-02, issue #170). A benchmark regression opens "Nightly benchmark regression on <ref>" and never fails the run. Naming the ref keeps branch and tag runs out of main's issue. Every PDF suite uses a fresh GitHub-hosted macOS Arm64 VM with explicit Rust, Node and external-tool setup. Python runs in a temporary venv. qpdf comes from a checksum-verified release; pdftotext is built from the checksum-verified Poppler source at the oracle pin, since Homebrew has moved on. veraPDF gets Java 21 explicitly.
- **Corpora (§3).** `fixtures/corpus-manifest.toml` lists pdf.js `test/pdfs`, PDFBox's PDFs, PDFium `testing/resources` and qpdf's `qtest` PDFs at pinned commits. It records each source's licence and every file's size and SHA-256 (2,172 files, 177 MB).
  - `cargo xtask corpus fetch` makes sparse, shallow, blob-filtered git checkouts. It always resets the remote to the manifest's URL. A checkout that no longer matches the manifest is restored from git (`reset --hard`, `clean`) before the run fails. A source that passed is stamped, so the differential only re-checks file sizes.
  - An optional mirror (`mirror` or `$LAMINA_PDF_CORPUS_MIRROR`, percent-encoded paths) is used only when git fails. A later fetch replaces the mirror download with a git checkout.
  - In CI the checkouts live in the runner's persistent tool cache (`$RUNNER_TOOL_CACHE/lamina-corpus`), so each night reuses or restores them instead of downloading them.
  - Not yet included: SafeDocs (multi-GB archives with mixed provenance), veraPDF and Arlington test files (with B8b), and PDFium's `.in` templates (they need PDFium's generator script).
- **Differential (tier 6).** `cargo xtask differential --live` runs lamina, pdf.js (`pdfjs-dist`), PDFium (`pypdfium2`), qpdf (`--json=2`) and pypdf over the external corpus and every `fixtures/corpus` mutant both PR lanes know: 250 per file from the fast set's series (whose first 4 are the fast set) and the full lane's 36. It compares the outcome, the page count and the outline titles. pdf.js and PDFium repair silently, so against them only readable vs failed counts. `--sample` is stratified per source.
  - **Isolation.** All readers run at once. Each works through chunks of inputs, one process per chunk under a time limit. A chunk that crashes, hangs or reports different files is rerun one file per process, so a bad file becomes a `timeout` or `crash` entry instead of stopping the run (`tools/xtask/src/runner.rs`).
  - **What fails a run.** A fact fails when every tool that compared it disagrees with lamina and no exception excuses it. A run also fails when lamina panics, crashes or hangs on a file, or when a reader breaks or reports the wrong files. The report is written either way.
  - **Splits.** A disagreement where some tool agrees with lamina is a split, listed in the report but not a failure: the tools differ from each other at least as much. The first full run had 436 failures and 1,890 splits before triage.
  - **Exceptions.** On top of the per-file `[[exception]]` entries of both exceptions files, `exceptions.toml` gains value-matched `[[class]]` rules and `[[known]]` entries. Each class names its ADR 0003 rule (for example "lamina repaired, the tool failed": §1 Repair). Each known entry is a bug or open question tracked by an issue, like an ignored flaky test (§4). The PR lanes apply an entry only if its `tools` include pypdf.
  - Text (B9c) and round-trip (B3c) join the same comparison when they land.
- **Fuzzing (tier 9).** Each target runs 10 minutes with `-timeout=10 -rss_limit_mb=2048`. The run starts from the target's last nightly corpus, or from the full lane's corpus saved on `main`. Only runs on `main` save it back: one entry per target, minimised first with `cargo xtask fuzz cmin`. Crashes are minimised under the same limits (`cargo xtask fuzz tmin`, skipping `slow-unit` files), uploaded, and quoted in the issue (base64 up to 4 KiB).
- **Scaling and benchmarks (tier 11).** `cargo xtask scaling` runs `cargo test --release -- --ignored` single-threaded and retries a failure once. A pass on retry is reported as flaky, never hidden.
  - `cargo xtask bench` runs the criterion benches in `crates/laminapdf-cos/benches/` (open + page-tree walk, Flate decode, building a file with `Writer`), `crates/laminapdf-save/benches/` (B3b's full rewrite in both xref layouts, and the incremental writer) and `crates/laminapdf/benches/` (B5d: the 100-page text report of pdf-library §4, the twin of `@laminapdf/sdk`'s `examples/report.ts`, and B6b's report of text boxes).
  - Each benchmark is compared with the median of its last five full (not `--quick`) records with the same runner label. A benchmark over 10% slower is a regression.
  - Benchmarks run on hosted Ubuntu x64 under `github-hosted/ubuntu-24.04-x64`. This starts a baseline separate from the earlier hosted macOS one (`github-hosted/macos-15-arm64`) and the former private Macs. GitHub's physical hosts vary, so timing regressions remain advisory.
  - The night's record is appended to `history.jsonl` on the `bench-data` branch. The token for that branch is passed per git command and only to the fetch and push steps, never to the step that builds and runs the benchmarks.
- **Proof record (T1a, 2026-11-08).** The night's robustness figures now leave the job summaries, whose artefacts expire, for one record that the website can publish (T1b). After every other suite, the `proof` job downloads each job's report and runs `cargo xtask proof`. The command writes one `kind: "proof"` record: Lamina PDF's outcomes per corpus source (opened, repaired, refused, refused while another reader opened the file, and panics, crashes or timeouts), the two differentials, the render diff, each fuzz target's run, veraPDF's validations, the round trip and the runtimes. The record holds counts, versions and results, never a corpus file name or text read from a file. A section whose report is missing is `null`, and the record's `jobs` gives each job's result, so a failed job never reads as a zero.

  The record's `full` flag is worked out from the reports. Every fuzz target must have run with a budget of at least 600 s, and each differential or render-diff report that exists must cover every input: unsampled, every source, and 20 pages per file. A missing report leaves its section `null` without making the night less than full, so a night with a failed job is still recorded. Only a full night on `main` appends the record to `history.jsonl` on `bench-data`; it has no `benches` key, so the benchmark comparisons pass over it. The round trip (tier 7) became a nightly job for the record's counts, and `extract` joined the fuzz matrix, which a test now holds to `harness::FUZZ_TARGETS`.

### Release guard accepts a full dispatched nightly (2026-11-02)

The release guard used to count only scheduled nightly runs, since a dispatched run can shorten the fuzz budget or sample the differential and render diff. GitHub, however, created the scheduled runs of 2026-10-31 and 2026-11-01 about 6.5 hours late and created none on 2026-11-02, which left the v0.2.0-alpha.1 release waiting on its queue. With the owner's approval, the guard now also accepts a `workflow_dispatch` run on `main` with every input at its default. nightly.yml's `run-name` titles such a run "Nightly (full budgets)" and every other dispatch "Nightly (short budgets)". The guard takes the newest completed run on `main` that is scheduled or carries that exact title, and applies the same rules as before: completed, successful, on `main`, and on the release commit or an ancestor. Dispatched runs from before nightly.yml had a `run-name` are titled "Nightly" and don't count. `tools/xtask/src/release.rs` tests the rule and the `run-name` expression.

### The web reader's release gates (C7c, 2026-11-10)

The reader's production deploy (`web-v*` tags, `.github/workflows/web-deploy.yml`) waits on three gates in its `production-checks` job, on the GitHub-hosted `ubuntu-24.04` runner the reader's workflow already uses (the repository is public, so hosted minutes cost nothing):

- **Startup size.** `cargo xtask web size`: the scripts the built `index.html` loads at startup, gzipped, against `apps/web/size-budget.json`. Bytes are deterministic, so the same check also fails pull requests: `cargo xtask pdf-runtimes` runs it after it builds the reader in the fast lane.
- **Lighthouse.** `lighthouse:local` serves the build with its deployed headers (`wrangler dev --local`) and asserts `lighthouserc.json`'s thresholds over three runs. PR previews run Lighthouse too, reported only.
- **Timings.** `cargo xtask viewer-perf --gate` runs the viewer's harness three times in Chromium and compares each figure's median with its web-app §4 target plus 25 %. A shared runner is noisier than a dedicated one: the median and the margin keep a slow neighbour from failing a release, while a real regression still shows. A miss fails the release unless `packages/viewer/perf/waivers.json` names it with an issue and the version that fixes it, with the owner's approval. The nightly keeps reporting the raw figures against the targets with no margin.

These are the only wall-clock checks that can fail a run, and they run only for a release tag, never on a pull request.
