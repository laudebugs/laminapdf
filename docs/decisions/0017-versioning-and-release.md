## Context

lamina ships one library through two ecosystems: the Rust crates (`laminapdf` and the core crates under it) and, when this ADR was written, two npm packages (`@laminapdf/wasm`, the WebAssembly modules built from `laminapdf-wasm`, and `@laminapdf/sdk`, the TypeScript API over them; the render packages joined later, see the amendment). They are one product: `@laminapdf/sdk` is only correct with the `@laminapdf/wasm` built from the same commit, and that module is the façade crate compiled to WebAssembly. The error contract ([ADR 0026](0026-error-and-diagnostic-contract.md)) and the op JSON ([ADR 0006](0006-op-log-and-undo.md)) are shared by every surface.

The [repo and packaging notes §5](../research/architecture/notes/repo-and-packaging.md#5-versioning-and-release-changesets-release-plz-cargo-release-semver-checks-provenance-trusted-publishing) compared the common setups: Changesets for npm and release-plz for crates (two tools, two release PRs, independent versions), or one lockstep version driven by Changesets with a script that writes it into `Cargo.toml`, "simpler when `@laminapdf/wasm` is tightly coupled to the core". The notes left open how Changesets handles Cargo packages: it doesn't; it only reads `package.json` files.

On 2026-10-28 the owner decided that nothing is published yet: crates and npm packages stay local (workspace and path dependencies, `pnpm pack` tarballs, git tags) until the owner decides to publish ([architecture: Publishing (later)](../plans/architecture.md#publishing-later)). So the first version, `0.1.0-alpha.0`, is versioned and tagged, and must be proven to install from outside the repository, without a registry.

[ADR 0018 §2](0018-test-strategy.md#2-ci-lanes) already defined a release lane on tags: the full and nightly suites on the release commit, packaging checks (publint, attw) and clean-install smoke tests in each runtime, and "a nightly failure … blocks the next release".

## Decision

### 1. One lockstep version

Every crate in the root Cargo workspace and the npm packages `@laminapdf/wasm`, `@laminapdf/sdk`, `@laminapdf/render`, `@laminapdf/render-hayro` and `@laminapdf/render-pdfium` share **one version** (the render packages since the 2026-10-31 amendment). A release bumps all of them together, even when a change touched one side only. Internal tools (`xtask`, `std14-gen`) are workspace members and carry the same number, which costs nothing (`publish = false`). Separate workspaces outside the lockstep keep their own versions: `fuzz/` (`laminapdf-fuzz`), `tools/render`, the spikes, and the docs app (`@laminapdf/docs`, ignored by Changesets).

One number means a user never has to work out which `@laminapdf/wasm` goes with which `@laminapdf/sdk`, or which crate version a WASM build came from; a bug report names one version.

### 2. Changesets drives the version; `cargo xtask version sync` copies it into Cargo

- **Changesets** (`@changesets/cli`, pinned exactly in the pnpm catalog; MIT) owns the version. `.changeset/config.json` puts those packages (six since `@laminapdf/viewer` joined) in one `fixed` group, so a changeset for any of them bumps all of them to the same version, and sets `privatePackages: { version: true, tag: true }`, because the packages are `private: true` until P1 and Changesets would otherwise skip them. Contributors add a changeset (`pnpm changeset`) with each user-visible change ([contributing: changesets](../guidelines/contributing.md#changesets)); `pnpm changeset version` consumes them, bumps every member's `package.json` and writes each package's `CHANGELOG.md`.
- **`cargo xtask version sync`** reads the fixed group from `.changeset/config.json` (exactly one `fixed` group, containing at least `@laminapdf/wasm` and `@laminapdf/sdk`; each member found by name under `packages/`, two folders with one member's name an error) and its version (every member's `package.json` must agree) and writes it into `[workspace.package] version` in the root `Cargo.toml`, the `version` of every internal `[workspace.dependencies]` entry (`path = "crates/…"`, which `cargo publish` will need), the internal crates' entries in every tracked `Cargo.lock` (the root's, `fuzz/`'s and the spikes'; edited in place: no network, no build, and `--locked` builds keep working), the root `CHANGELOG.md` (§4), and the string literal of `export const VERSION = "…"` in `packages/sdk/src/version.ts` (the version `@laminapdf/sdk/worker`'s handshake compares; Changesets doesn't know it; a constant rather than a JSON import of `package.json`, which would change how each export condition bundles). The edits are line based, so the manifest's comments survive, and the result is parsed back and checked.
- **`cargo xtask version sync --check`** runs in `cargo xtask check docs` (so in every PR, in both lanes): it fails, naming each file, when a sync would change anything, and when a member crate sets its own version instead of `version.workspace = true`. A version edited by hand anywhere fails CI.

The release preparation is therefore `pnpm changeset version`, then `cargo xtask version sync`, committed together in one PR.

### 3. `0.x` semantics and pre-releases

- Versions follow [SemVer 2.0](https://semver.org/spec/v2.0.0.html) with Cargo's reading of `0.x`: while the major version is 0, a **breaking change bumps the minor** version (`0.1 → 0.2`), and features and fixes bump the patch (`0.1.0 → 0.1.1`). In Changesets terms: `minor` for a breaking change, `patch` for everything else, and never `major` before the owner decides on 1.0.
- **Pre-releases** use the `alpha` identifier, numbered from 0: `0.1.0-alpha.0`, `0.1.0-alpha.1`, … Changesets' pre mode (`pnpm changeset pre enter alpha`, recorded in `.changeset/pre.json`; consumed changesets move to `.changeset/pre/`) produces them; `pnpm changeset pre exit` ends it before `0.1.0`. Cargo and npm both order `0.1.0-alpha.1` below `0.1.0`; the internal dependencies name the exact version anyway (`version sync`, and `pnpm pack` turns `workspace:*` into it).
- What `0.x` promises beyond SemVer (error and warning codes, op JSON versions) is in the [stability policy](../stability-policy.md), in force since the first registry release, `0.2.0-alpha.1` ([P2](../todos/done/P2-first-registry-prerelease.md)).

### 4. Changelog

Changesets writes each member's `packages/<name>/CHANGELOG.md` from the changesets (the default `@changesets/cli/changelog` generator: no GitHub API, no token). A changeset lists only the packages it names, so a fix to `@laminapdf/render` leaves `@laminapdf/sdk`'s changelog with an empty heading for that version. `cargo xtask version sync` therefore merges every member's changelog into the root [`CHANGELOG.md`](../../CHANGELOG.md), the library's changelog: per version, newest first (SemVer order), the union of the members' entries under Major, Minor and Patch Changes, each entry once, without Changesets' dependency-bump entries ("Updated dependencies", `- @laminapdf/wasm@…`), which say nothing in lockstep; a version without entries says "No changes in this release." Nobody edits a changelog by hand; the changesets are the source.

### 5. Tags

A release is tagged `v<version>` on its release commit, e.g. `v0.1.0-alpha.0`: one tag for the whole library. `cargo xtask version check-tag <tag>` fails unless the tag names the current version. Changesets' own per-package tags (`@laminapdf/sdk@…`, `changeset tag`) are not used.

The daily release makes the release commit and its tag (amended 2026-11-05). It runs when a full nightly run on `main` succeeds, the same runs the guard of §6 counts, and only while changesets are waiting. `cargo xtask release prepare` refuses while a version pull request is open or the next tag exists. On a branch `release/v<version>` from the nightly's commit, it runs `pnpm changeset version` and `cargo xtask version sync` and commits the result. A release bot, a GitHub App with contents and pull-request permissions on this repository, then pushes the branch and the tag: a push with the workflow's own token would start no other workflow. Once the lane has published, the bot's version pull request merges the bump into `main` like any other pull request. The tagged commit is the nightly's tree plus the version bump, and the squash puts a copy of that change on `main`. The repository variable `RELEASE_TRAIN=off` stops the daily release, and the owner, or an agent with the owner's permission, can still tag a release by hand.

### 6. The release lane

`.github/workflows/release.yml` runs on `v*` tags (and on `workflow_dispatch`, with an optional `ref` input, to try it on a branch or an existing tag):

1. **Guard.** `cargo xtask release-guard` asks GitHub (`gh run list --workflow nightly.yml --branch main --status completed`) for the latest completed **full** nightly run on `main` and refuses to go on unless it succeeded on the release commit or an ancestor of it (`git merge-base --is-ancestor`); `--run <id>` checks one given run under the same rules (how the guard is tested). A full run is scheduled, or dispatched with every input at its default (titled "Nightly (full budgets)"; amended 2026-11-02, see [ADR 0018's implementation notes](0018-test-strategy.md#release-guard-accepts-a-full-dispatched-nightly-2026-11-02)). Then `version check-tag` for a tag.
2. **The fast lane** (`cargo xtask check`, `wasm` with publint `--strict` and attw `--pack`, `size`), **the full lane's suites** (full differential, fuzz at main's budget, round trip, examples and render goldens, capability matrix, `@laminapdf/sdk` in every runtime, `check` on Linux while that runner is on) and **the nightly lane** itself (`nightly.yml`, called as a reusable workflow with `record: false`, so it pushes no benchmark history, saves no fuzz cache and opens no issue, in its own concurrency group) on the release commit. The lane skips that nightly run when `cargo xtask release-guard --version-only` finds that the release commit differs from the commit the guard's nightly passed on only in the files a version bump writes: the fixed group's versions in `package.json` and Cargo files, the changelogs, `.changeset/` and `packages/sdk/src/version.ts` (amended 2026-11-05). The daily release's commits always qualify.
3. **`cargo xtask verify-install`**: `pnpm pack` tarballs of `@laminapdf/wasm` and `@laminapdf/sdk` (the render packages are not install-verified yet) and the `laminapdf` crate as a `path =` and a `git =` dependency (pinned to the tag) in clean projects outside the checkout, running the quick start in Node 22, 24 and 26, Deno, Bun, Chromium (a Vite production build), workerd (`wrangler dev --local`) and a Rust binary; every output must be byte-identical to `fixtures/golden/examples/hello.pdf`.
4. **The publish jobs** of §7, once the `release` job reports that every check passed (until P1, the lane published nothing), then the docs deploy of §7 and, for a daily release, the version pull request of §5.

### 7. Publishing

The owner decided on 2026-11-01 to publish the crates and the npm packages, from a repository that stays private for now. The release lane therefore publishes with short-lived or narrow credentials, and approval stays with the owner. The last item lists what the private repository can't have yet (npm provenance, GitHub artifact attestations, a required reviewer on an environment) and what switches it on.

- **What is published.** Twelve crates have `publish = true`: `laminapdf` and `laminapdf-syntax`, `-cos`, `-model`, `-ops`, `-content`, `-text`, `-build`, `-save`, `-render`, `-render-pdfium` and `-source`. On npm, the fixed group of §1 is published: `@laminapdf/wasm`, `sdk`, `render`, `render-hayro`, `render-pdfium` and `viewer`. The binding crates (`laminapdf-wasm`, `laminapdf-render-wasm`) are reserved on crates.io but not published; they reach users inside `@laminapdf/wasm`. Every crate name was reserved with a `0.0.0` placeholder from the owner's account, which crates.io's trusted publishing needs before it can be configured.
- **When.** Only a `v<version>` tag push publishes (`github.event_name == 'push' && github.ref_type == 'tag'`). The publish jobs run after the `release` job, so every check of §6 must pass first. A `workflow_dispatch` run of the lane, even on a tag, does everything with `--dry-run`. A re-run after a partial publish leaves out the crates and npm packages already at the version. The owner approved automatic releases on 2026-11-05: a tag the release bot pushes after a passing nightly (§5) publishes with no further approval, and a tag the owner pushes is the owner's own.
- **crates.io: trusted publishing.** `publish-crates` exchanges the workflow's OIDC token for a short-lived crates.io token (`rust-lang/crates-io-auth-action`; with `publish-npm`, one of the two jobs with `id-token: write`). It then runs `cargo xtask publish crates`, which is `cargo publish --workspace --locked`: every crate in dependency order, each built from its packaged files first. crates.io accepts self-hosted runners and private repositories, and each crate's trusted publisher is `laudebugs/laminapdf`, workflow `release.yml`. No crates.io token is stored. Two packaging rules follow. Dev-dependencies on workspace crates are by path only, so `cargo publish` drops them and the tests' cycles never reach crates.io. And a crate includes no file outside its folder: `laminapdf`'s `explain` pages are generated as raw strings.
- **npm: trusted publishing from a GitHub-hosted runner** (amended 2026-11-05; until then, staged publishing with a stage-only token, each version approved by the owner on npmjs.com). npm's trusted publishing accepts only cloud-hosted runners, so the work splits in two. On the self-hosted Mac, `cargo xtask publish npm-pack` builds the packages, packs each with `pnpm pack` (which turns `workspace:*` into the version) and writes the publish order, dependencies first; the tarballs go up as an artifact. Then `publish-npm` runs on a GitHub-hosted runner with `id-token: write`: it checks out nothing, downloads the tarballs and runs `npm publish --access public` for each in order (npm 11.5.1 or later, which exchanges the workflow's OIDC token for a short-lived one). No npm token is stored, the job runs no code from the repository, and no version waits for an approval. A pre-release goes under its pre-release identifier as the dist-tag (`alpha`), so `npm install` never picks it by default. Each package's trusted publisher on npmjs.com is `laudebugs/laminapdf`, workflow `release.yml`. Trusted publishing works from a private repository, but provenance needs a public one (last item).
- **Docs** (amended 2026-11-05). `docs.laminapdf.com` documents the latest release: the lane deploys the docs from the release commit once the packages are published, and every page names that version. Every push to `main` deploys `next.docs.laminapdf.com`, which documents what is merged but not yet released, says so on every page and is never indexed ([ADR 0011 §1](0011-cloudflare-topology-and-privacy.md#1-topology)).
- **The GitHub release.** `github-release` writes a CycloneDX SBOM for every published crate (`cargo-cyclonedx`, pinned in `doctor.rs`) and npm package (`pnpm sbom`), and creates the GitHub release for the tag, with the version's section of `CHANGELOG.md` and the SBOMs attached; pre-release versions are marked as such. A dry run uploads the SBOMs as an artifact.
- **Later, once the repository is public:** npm provenance (the trusted publishing above generates it once the repository is public), GitHub artifact attestations for the `.wasm` files and the tarballs, and a `release` environment that keeps the release bot's key from other workflows (amended 2026-11-05: this item named a required reviewer on that environment until the owner chose automatic releases).

## Consequences

- One number for the whole library; the sync is a few hundred lines of tested xtask code instead of a second release tool. A version bump touches every crate even when only TypeScript changed; that's the price of lockstep, and cheap while nothing is published.
- Contributors must add a changeset to user-visible changes; forgetting one only means the change is missing from the changelog (nothing fails, by choice: docs, CI and internal refactors need none).
- Changesets' pre mode leaves `.changeset/pre.json` and `.changeset/pre/` in the tree while the version is an alpha.
- `version sync --check` makes a hand-edited version fail every PR, so the two ecosystems can't drift.
- The release lane is long (the nightly suites alone take hours on the shared Mac runners) and is refused while the nightly lane is red; fixing the nightly comes first.
- The release lane publishes from P1 on, and the first registry release is P2. From P6 on it releases at most once a day, after the nightly, with no human step (amended 2026-11-05); the release bot's key is the one secret it keeps, and the npm job uses a few GitHub-hosted minutes a release.

## Alternatives considered

- **Changesets for npm and release-plz for the crates** (the notes' first option): two tools, two release PRs and independent versions for products that only work at matching versions. release-plz's strengths (per-crate changelogs, publishing) only matter once crates are published and versioned apart; they can be revisited if a crate ever needs its own cadence.
- **cargo-release or a Cargo-first sync (Cargo writes `package.json`)**: Changesets is the only tool with a contributor workflow (one file per change, written in the PR), and the npm side needs it anyway; one direction of sync is simpler than two.
- **Independent versions with a compatibility table**: more numbers to explain, and every bug report would need three versions.
- **`toml_edit` for the manifest edits**: a new dependency for edits a line-based rewrite does safely (it is parsed back and checked) on a manifest we control.
- **Changesets' per-package tags** (`@laminapdf/sdk@0.1.0-alpha.0`): one product, one tag; `v<version>` also names the crates' version.
- **Publishing the alpha**: ruled out by the owner for now (2026-10-28).
