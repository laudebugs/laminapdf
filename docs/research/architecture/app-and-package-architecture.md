# One Rust core powers three Lamina products

Lamina should be built as **one permissively licensed Rust document engine with three thin shells around it**. The engine is a lazy COS object layer, a typed model, an operation log with undo, and a save planner. The first shell is a framework-light TypeScript viewer/editor that runs the engine as WASM in a Web Worker and is served free from Cloudflare Workers static assets. The second is a Tauri 2 desktop app that links the same crates natively and gets updates from a Worker backed by R2. The third is a set of importable packages (`lamina-*` crates, `@lamina/*` npm) that ship the same core without any UI. Rendering is the one subsystem Lamina should not build first. It sits behind a `RenderBackend` trait, with **PDFium as the shipping default** in both apps: PDFium is Apache-2.0, has high fidelity, and supports forms and annotations. **hayro** (pure Rust, MIT/Apache, 0.8.0) runs in CI as a differential oracle and becomes the default once it reaches parity. **MuPDF is excluded** because it is AGPL. This shape is what lets ~180 operations in 13 groups land incrementally without forking the codebase: every feature is a typed op in the core, so the web app, the desktop app and the npm/crate API all get it at once. Cloudflare's role is deliberately small and privacy-first. Hosting and downloads cost almost nothing. The opt-in server tier uses Durable Objects for annotation sync, R2 for blobs, D1 for metadata, and Containers for the heavy jobs (OCR, Office conversion) that cannot fit in a Worker's 128 MB. The largest risks are three. Linux WebKitGTK rendering may be fragile under Tauri. Running PDFium beside Lamina's own parser creates a "two parsers" problem for live editing. And the WASM build is capped at 4 GB of memory because Safari still lacks Memory64. Each risk has a named mitigation and a decision to record as an ADR.

## The reference architecture is one engine with three shells

The prior research already settled the core language. Chapter 05 recommends a Rust core, dual MIT/Apache-2.0, compiled to native and `wasm32`, with TypeScript as the first binding, because "the permissive, full-stack slot is empty" and licence drift (QuestPDF, PDFsharp→AGPL) is a real hazard ([05 §8](../pdf/05-creating-pdfs-from-code.md)). The spike proved the mechanics. One spec was implemented in both languages: the Rust core compiled to **172 KB of WASM (74 KB gzipped)**, was called from TypeScript through a four-function C ABI, produced byte-identical output, and agreed with the TypeScript reader on **4,304 of 4,305** differential-fuzz inputs ([07 §3](../pdf/07-spike-rust-and-typescript.md)). The architectural question is therefore not *whether* to share a core, but where the seams go so that two apps and a library family can grow from it.

The answer is the layering the feature inventory already sketched, a UI over six engines that share one object model ([06 §8](../pdf/06-feature-inventory.md)), made concrete as crates and shells:


Three seams carry the design. The first is **bytes in, bytes out**. The spike already enforced it: no file system, network, clocks or thread *spawning* in library code (the core's types are `Send` where possible, so a shell may run independent work, such as rendering separate pages, on several threads or workers, but the core never creates threads itself) ([07 §1](../pdf/07-spike-rust-and-typescript.md)). That rule is what makes the same crate run in a browser worker, a Cloudflare Worker, a Tauri process and, later, a UniFFI mobile app. I/O enters only through two traits. A `ByteSource` supports range reads: mmap on desktop, `Blob.slice`/OPFS on the web, HTTP range in a Worker. A streaming `WriteSink` is modelled on PDFium's `FPDF_FILEWRITE` callback ([PDFium fpdf_save.h](https://pdfium.googlesource.com/pdfium/+/refs/heads/main/public/fpdf_save.h)). The second seam is a **handle-based façade** with owned types and byte buffers. It maps one-to-one onto wasm-bindgen classes, Tauri commands and UniFFI, so the API is designed once ([desktop notes, UniFFI 0.32 `ForeignBytes`](https://docs.rs/crate/uniffi/latest)). The third seam is the **op stream**. Every mutation is a serialisable typed `Op`, so undo, dirty tracking, collaboration sync and the public API all consume the same thing.

The hot path never touches a UI framework, and that is the key structural choice on the client. pdf.js, Figma, tldraw and EmbedPDF all separate an imperative engine-driven canvas from framework-rendered chrome, and EmbedPDF ships React, Vue and Svelte adapters over one headless PDFium core ([EmbedPDF docs](https://www.embedpdf.com/docs/svelte/introduction)). Lamina's page virtualizer, canvas pool, text layer and annotation layer should be plain TypeScript modules driven by worker messages. That makes the framework choice reversible and lets third parties embed the viewer.

## PDFium ships now, hayro is the destination, and a trait decides

No permissive engine today offers both pure-Rust safety and editor-grade features, so the rendering decision is a sequencing problem. **pdf.js 6.4.299** (3 Oct 2026, Apache-2.0) is the most actively released engine, now with annotation editing, signature verification and merging ([pdf.js releases](https://github.com/mozilla/pdf.js/releases)). But it is JavaScript and cannot share a model with a Rust core, so Lamina would carry two document models that could drift. **PDFium** through EmbedPDF's MIT wrapper (`@embedpdf/pdfium` 2.15.1) provides rendering, text extraction and search, form filling, annotation CRUD, signature verification and modification ([npm](https://www.npmjs.com/package/@embedpdf/pdfium); [README](https://cdn.jsdelivr.net/npm/@embedpdf/pdfium@2.14.3/README.md)). Natively it is reachable through `pdfium-render` 0.9.4, which recently fixed double-frees and WASM memory-growth issues ([docs.rs](https://docs.rs/crate/pdfium-render)). The cost is size: **`pdfium.wasm` is 4,632,999 bytes raw** ([jsDelivr](https://www.jsdelivr.com/package/npm/@embedpdf/pdfium)), reported at roughly 2.7 MB gzipped ([HN](https://hn.nuxt.dev/item/44126177)), which is about 37× the spike's core. **hayro 0.8.0** (4 Oct 2026, MIT/Apache) claims that almost anything Chrome or Firefox renders will render correctly, backed by a 1,600+ PDF regression suite. It is still CPU-only, renderer-only, publishes no pass/fail table, lacks glyph caching, and its demo has no text selection, search, annotations or forms ([hayro](https://github.com/LaurenzV/hayro)). **MuPDF.js 1.28.1** is AGPL-3.0-or-later, and Artifex states that linking code must also be AGPL, including over a network ([MuPDF licence](https://mupdf.readthedocs.io/en/1.27.0/license.html)). That disqualifies it for an MIT/Apache project.

The recommendation is a `RenderBackend` trait with PDFium as the default adapter in both apps. That means native PDFium via `pdfium-render` on desktop and PDFium-WASM in the web worker. hayro is wired in as a second adapter from day one and diffed against PDFium over the pdf.js and PDFBox corpora that hayro itself uses. This **revises chapter 05's "rendering via hayro" recommendation** for the *apps* only ([05 §8.6](../pdf/05-creating-pdfs-from-code.md)). For the *packages*, hayro remains the natural optional renderer, because it keeps the npm and crate footprint pure-Rust and small. The reason for the reversal is that a reader that grows into an editor needs fidelity and a long tail of real-world files on day one. The rendering notes find no current neutral fidelity benchmark of pdf.js vs PDFium vs hayro ([dev.to](https://dev.to/feed/9haroon)), so Lamina's own corpus-diff harness becomes the instrument that eventually justifies switching the default.

The trait's surface is copied from what every serious viewer does: render a page rectangle at a scale, with or without annotations, into a caller-supplied RGBA buffer. PDFium's `FPDF_ANNOT` flag already separates annotation rendering, so live annotations can be DOM/SVG while flattened content stays raster ([EmbedPDF engines](https://www.embedpdf.com/docs/engines/introduction)). Text runs with character boxes, the struct tree, and annotation and field geometry come from Lamina's own model, not from the renderer. Hit-testing then runs on document geometry rather than pixels, and accessibility does not depend on which backend is active.

**The two-parsers problem is the architecture's sharpest edge.** If Lamina's core owns editing and PDFium owns rendering, the renderer has to see edits. Most edits are cheap. Annotations and form values render as overlays from Lamina's model until save. Page operations (reorder, rotate, delete, insert) are a view-level mapping from stable page IDs to source pages, so they need no re-parse. Content edits (phase 4) and applied redactions do change the bytes the renderer must draw. For these, the core emits an incremental update through `WriteSink` and the renderer reloads the touched pages. For huge files this means reloading from a `ByteSource` rather than from a copied buffer. That works but must be measured early. It is also the strongest long-term argument for hayro: built on `hayro-syntax`, a pure-Rust renderer could eventually read Lamina's object graph directly ([docs.rs hayro](https://docs.rs/hayro)).

## Tauri 2 and a framework-light web client share 90% of the UI

### Tauri 2 is the desktop shell, with Electron held in reserve for Linux

Tauri's selling point for Lamina is not smaller downloads. It is that **`src-tauri` links `lamina-core` natively** while reusing the web UI package. Tauri core is at **2.12.5 (21 Oct 2026)**, with v3 in alpha showing only dependency churn ([Tauri releases](https://github.com/tauri-apps/tauri/releases)). Size claims need tempering. In Better Stack's July 2026 test the Tauri bundle was 57 MB vs Electron's 323 MB, but memory was **~109 MB vs ~128 MB**: "runtime memory footprints are much closer than on-disk sizes" ([Better Stack](https://betterstack.com/community/guides/scaling-nodejs/tauri-vs-electron-vs-deno-vs-electrobun/)). The closest domain peer, Stirling-PDF, keeps a `frontend/src-tauri` desktop build inside its web frontend package, which is exactly the sharing Lamina wants ([Stirling-PDF](https://github.com/Stirling-Tools/Stirling-PDF/tree/main/frontend/src-tauri)). Electron 45 (Chromium 156) would give uniform rendering on all three OSes ([Electron blog](https://www.electronjs.org/blog)). But it would reach the Rust core only through napi-rs or WASM, adding a binding layer for no feature gain. Native per-OS UIs (SwiftUI/WinUI/GTK) would mean four UIs. Rust-native toolkits give up the shared web UI: GPUI has no official crate and is pre-1.0 ([lib.rs](https://lib.rs/crates/gpui-unofficial)), and Slint's royalty-free licence requires attribution ([Slint](https://slint.dev/agreements/slint-royalty-free-license.pdf)).

The real Tauri risk is **Linux WebKitGTK**. Tauri's own docs (updated June 2026) list blank windows, resize crashes and DMABUF/Wayland errors, mostly on NVIDIA, and warn that "WebGL and canvas content can silently fall back to a slow path." They recommend shipping a non-WebGL fallback and a user-facing renderer switch ([Tauri Linux graphics](https://v2.tauri.app/develop/debug/linux-graphics/)). WebKitGTK has no shipped WebGPU ([WebKit 257694](https://bugs.webkit.org/show_bug.cgi?id=257694)). Lamina's architecture already absorbs this: pages are rasterised by the Rust renderer and drawn with Canvas2D `drawImage`, and GPU paths are only an enhancement. If Linux support becomes a burden, the documented fallbacks in order are Tauri with the CEF runtime (not yet production-ready), Electron on Linux only, then Electron everywhere.

The desktop data path follows from Tauri's IPC rules. Serde return values are serialised to JSON, which "can slow down your application if you try to return large data". Raw bytes must go through `tauri::ipc::Response`, and **Channels are the recommended streaming mechanism** ([Tauri calling Rust](https://v2.tauri.app/develop/calling-rust/)). A third-party benchmark puts 64 KB at ~202 µs over a binary path vs 2.27 ms over default invoke ([tauri-conduit](https://github.com/userFRM/tauri-conduit)). An A4 page at 2× DPR is about 15 MB of RGBA, so the desktop adapter sends **256–512 px tiles**. These go either as raw RGBA over a Channel into `createImageBitmap`, or as compressed tiles from a `lamina://tile/{doc}/{page}/{zoom}/{x}/{y}` custom scheme that the webview fetches like images. wry supports streaming and ranged responses on custom schemes ([wry streaming example](https://docs.rs/crate/wry/0.56.0/source/examples/streaming.rs)). The native side memory-maps 1 GB files with `memmap2`, watches them with `notify`, and runs parsing and rendering in a **separate child process**, copying Chrome's sandboxed out-of-process PDF viewer so a hostile file crashes a worker and not the app ([Chromium pdf/README](https://chromium.googlesource.com/chromium/src/+show/f303bc03a281b55dbd066185f79daa61dd8ba8d1/pdf/README.md)).

The rest of the desktop surface is configuration. File associations deliver `RunEvent::Opened` on macOS, and on Windows/Linux paths arrive as argv, so `single-instance` with its `deep-link` feature forwards them to the running window ([Tauri deep-linking](https://v2.tauri.app/de/plugin/deep-linking/)). Distribution starts as Developer ID + notarisation outside the Mac App Store, because MAS forces App Sandbox and disables the self-updater ([Tauri App Store](https://v2.tauri.app/distribute/app-store/)). Windows signing uses Azure **Artifact Signing** via `bundle.windows.signCommand`. Its public-trust *individual* tier is limited to the US and Canada, and organisations need US/Canada/EU/UK presence ([Microsoft quickstart](https://learn.microsoft.com/azure/artifact-signing/quickstart)), so the signing identity is an early governance decision. Linux ships AppImage, which the updater requires ([Tauri updater](https://v2.tauri.app/plugin/updater/)), plus deb/rpm, with Flatpak optional. **Printing is unresolved.** Tauri has no first-class print API beyond `window.print()` (unverified in the notes), and faithful PDF printing likely needs per-OS native paths. It deserves its own spike.

### The web client is React chrome around an imperative viewer core

On the web, the framework decision matters less than it appears, because a virtualised viewer mounts only a few dozen page shells. **React 19 with React Compiler 1.0** (stable 7 Oct 2025, [react.dev](https://de.react.dev/blog/2025/10/07/react-compiler-1)) is the default for app chrome. The reasons are ecosystem ones: the largest contributor pool, mature accessible primitives (React Aria, Radix, Base UI), and an existing EmbedPDF adapter. Solid and Svelte 5 lead on raw benchmarks, but the figures differ between secondary sources ([tech-insider](https://tech-insider.org/svelte-vs-react-2026/)). Solid 2.0 is still at rc builds ([socket.dev](https://socket.dev/npm/package/solid-js/overview/2.0.0-rc.5)), so its advantage does not outweigh contributor reach for an open-source editor. Interaction modes (select, ink, form-fill, redact) belong in a state machine. View state belongs in a signal or external store read via `useSyncExternalStore`. The document itself lives in the worker.

The viewer core follows the layering every engine converged on. A raster canvas sits underneath. Above it are a transparent DOM text layer for native selection, find, copy and screen readers, then an SVG/DOM annotation layer, then DOM form widgets ([Mozilla](https://blog.mozilla.org/attack-and-defense/?p=253)). A struct-tree layer is linked via `aria-owns`, as pdf.js does, which means the core must expose `StructTreeRoot` and `MarkInfo` ([pdf.js #6269](https://github.com/mozilla/pdf.js/issues/6269)). Rendering uses a prefix-sum page virtualiser with zoom anchoring and a pooled set of canvases. The worker rasterises into WASM memory and posts transferable `ImageBitmap`s. A low-resolution pass precedes sharp tiles. OffscreenCanvas is available everywhere, including Safari since 16.4 ([web.dev](https://web.dev/articles/offscreen-canvas)), so it remains an option, but transferring bitmaps keeps pooling simpler.

The worker boundary is a **hand-written typed RPC** rather than Comlink. It carries request IDs, transfer lists, priority queues and `AbortSignal` cancellation, so that fast scrolling cancels stale render jobs. **SharedArrayBuffer and WASM threads are an optional enhancement owned by the shell, not the core.** The threaded build is the same single-threaded core instantiated in a pool of workers that share memory, so independent pages parse and render in parallel; the core itself still spawns nothing (consistent with bytes-in/bytes-out). They require COOP/COEP. Cloudflare static assets can set those headers via `_headers`, though Worker-generated responses must set them in code ([Cloudflare headers](https://developers.cloudflare.com/workers/static-assets/headers/)). Tauri ≥2.1 sets them via `app.security.headers` ([Tauri headers](https://v2.tauri.app/security/http-headers/)). But COEP `require-corp` breaks OAuth popups and cross-origin assets, and no source confirms that every Tauri webview reports `crossOriginIsolated === true`. Lamina therefore builds a single-threaded WASM baseline and a threaded variant selected at runtime.

File access follows the platforms. **OPFS** with worker-only `createSyncAccessHandle` is supported in all engines (Firefox 111, Safari 15.2) and is the engine's scratch store and random-access cache ([web.dev OPFS](https://web.dev/opfs)). `showOpenFilePicker` is still "not Baseline" ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/showOpenFilePicker)), so Safari and Firefox fall back to input, drag-drop and download-to-save. A runtime `Platform` adapter exposes capability flags (`canWriteInPlace`, `canWatchFiles`, `hasNativePrint`, `multiWindow`) so UI code never branches on "is this Tauri". The build uses **Vite 8**, whose single bundler is now Rolldown ([Vite blog](https://vite.dev/blog/announcing-vite8)), with Vitest browser mode and Playwright across Chromium, WebKit and Firefox.

## Editing is an op log over a lazy object graph, and signatures and redaction govern saving

Chapter 06 ranks in-place content editing as the hardest feature and lists the correctness traps: redaction that only covers content, incremental saves that keep "deleted" content, and saves that break signatures ([06 §7, §10](../pdf/06-feature-inventory.md)). The editing architecture exists to make those traps unrepresentable. Every mature engine keeps a COS object graph under a typed model and supports two save modes. PDFium exposes them as mutually exclusive `FPDF_INCREMENTAL`/`FPDF_NO_INCREMENTAL` flags ([fpdf_save.h](https://pdfium.googlesource.com/pdfium/+/refs/heads/main/public/fpdf_save.h)). LibPDF defaults to full rewrite and admits it "cannot automatically detect when incremental saves are required" ([LibPDF](https://libpdf.documenso.com/docs/concepts/incremental-saves)). PDFBox's incremental save depended on callers flagging changed objects by hand, and a bug report says changes were "most of the time … completely ignored" ([PDFBOX-5263](https://issues.Apache.org/jira/browse/PDFBOX-5263)). The lesson is that dirty tracking must be automatic at the COS mutation API. Separately, lopdf's eager whole-document model ([docs.rs lopdf](https://docs.rs/lopdf/latest/lopdf/)) does not fit large files in WASM, so Lamina builds its own **lazy COS layer**: objects parse on demand from a `ByteSource`, and every write lands in an overlay map `ObjRef → New | Modified | Deleted` above an immutable base revision. The spike already has the incremental writer and repair logic this extends ([07 §1](../pdf/07-spike-rust-and-typescript.md)).

Above COS sits the **semantic op log**: typed ops such as `AddAnnot`, `SetField`, `MovePage`, `EditContent`, `MarkRedaction`, `ApplyRedactions` and `Sign`. They are grouped by `doc.transact(|tx| …)` into transactions that roll back the overlay on error and record inverse ops for undo. Undo follows Figma's rule that inverse ops are computed from current state at undo time ([Figma](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)), and Yjs's rule that undo is scoped to the local origin and ignores remote changes ([Yjs UndoManager](https://docs.yjs.dev/api/undo-manager)). Two op classes are **barriers**. `ApplyRedactions` is irreversible once saved, as Apryse's API states ([Apryse](https://docs.apryse.com/web/guides/features/redaction/redact)). `Sign` freezes a byte range. Before save, undo can drop either from the overlay. After save, the undo stack is segmented. Stable `LaminaId`s (`/NM` on annotations, a sidecar map for pages) keep ops valid across reorders and give sync a key.

The **save planner** turns these rules into a document-level `SaveConstraint`. A document with no signatures is `Free`. A signed document is `AppendOnly`: only incremental saves are allowed, and ops are restricted by DocMDP/FieldMDP, because signatures cover byte ranges that a rewrite moves (ISO 32000-1 §12.8.1 `/ByteRange`; §7.5.6 incremental updates; DocMDP and FieldMDP in §12.8.2.2 and §12.8.2.4; see also [chapter 04 §8](../pdf/04-interactive-security.md) and [LibPDF](https://libpdf.documenso.com/docs/concepts/incremental-saves)). A document with pending applied redactions or decryption is `RequiresRewrite`, because an incremental update leaves all earlier revisions in the file (§7.5.6), so redacted bytes only disappear in a full rewrite (redaction annotations: §12.5.6.23; why covering is not redacting: [chapter 04 §10](../pdf/04-interactive-security.md)). When a user redacts a signed document, the UI must warn that the signatures will be invalidated. The canonical order is **redact → full rewrite → sign → incremental save**. Signing is two-phase: prepare the `/Contents` placeholder and ByteRange, then hand off to WebCrypto, an HSM or a server signer, then inject the signature. PDFBox 3 converged on the same external-signing model ([PDFBox notes](https://apache.googlesource.com/pdfbox/+/trunk/RELEASE-NOTES.txt)).

**Collaboration is server-authoritative and record-based, not a CRDT over PDF bytes.** Figma uses one authoritative process per document with last-writer-wins per (object, property) and fractional indices for ordering ([Figma](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)). tldraw's Cloudflare template runs **one Durable Object per room**, persisted with `SQLiteSyncStorage`, with hibernation and schema migrations ([tldraw sync](https://tldraw.dev/docs/sync)). Nutrient syncs annotations as Instant JSON over an immutable PDF ([Nutrient](https://nutrient.io/guides/web/instant-synchronization)). Lamina follows the same pattern. Base PDF bytes are content-addressed and immutable in R2. A "layer document" of annotation, field-value and page-order records is synced through a per-document Durable Object, with property-level LWW, deletes that win, and fractional indices for page order. Flattening into PDF bytes happens at save or export through the core. Content-stream edits and applied redaction are not mergeable. They take a lease, or run as a server job that mints a new base revision. PDF bytes never cross the socket, since a DO accepts at most **32 MiB per WebSocket message** ([DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/)). A CRDT (Loro, or Automerge 3, which cut memory more than 10× ([Automerge](https://automerge.org/blog/automerge-3/))) is worth adopting only if peer-to-peer or long-offline editing becomes a requirement. Both are Rust and could live in the same WASM module.

Two constraints bound where operations run. **Memory64 is unsupported in Safari** desktop through 27.1 and iOS through 27.2 ([caniuse](https://caniuse.com/wf-wasm-memory64)), so the web engine is wasm32 with a 4 GB ceiling. It must stream from `ByteSource` and write through `WriteSink` rather than hold whole documents. And untrusted input demands an explicit **`Limits`** struct (nesting depth, filter-chain length, decompressed bytes, xref entries, page-tree depth, ops per page, a fuel budget). That mirrors qpdf's 2026 hardening: page-tree depth limits in 12.4.0, and a 25-filter cap plus a global limits API in 12.3.0 ([qpdf release notes](https://qpdf.readthedocs.io/en/stable/release-notes.html)). The spike already found that "every number read from the file is an attacker-controlled allocation size" ([07 §4](../pdf/07-spike-rust-and-typescript.md)).

## Cloudflare hosts everything for about $5 a month, with heavy jobs in Containers

Cloudflare's own docs now steer new projects away from Pages ("Start new projects with Workers") ([Pages](https://developers.cloudflare.com/pages/)). The web app is therefore one Worker with static assets: `not_found_handling: "single-page-application"` and `run_worker_first: ["/api/*"]` ([SPA routing](https://developers.cloudflare.com/workers/static-assets/routing/single-page-application/)). **Static asset requests are free and unlimited** ([pricing](https://developers.cloudflare.com/workers/platform/pricing/)), and each asset may be up to **25 MiB**, so the 4.6 MB PDFium WASM fits ([limits](https://developers.cloudflare.com/workers/platform/limits/)). The default build has no `/api` routes and uploads nothing: PDFs are processed client-side in WASM. Every server feature is opt-in. The new `cf` CLI entered beta on 2026-09-28 and warns that "commands, configuration, and Build Output may change" ([changelog](https://developers.cloudflare.com/changelog/post/2026-09-28-cloudflare-cli-beta/)), so CI pins Wrangler and tries `cf migrate` on a branch.

| SPA, WASM, fonts | Workers static assets | Free/unlimited requests; 25 MiB per file; 100k files (Paid) ([limits](https://developers.cloudflare.com/workers/platform/limits/)) |
| PDF blobs, installers, corpus | R2 | $0.015/GB-month, **free egress**; presigned URLs only on the S3 endpoint, 7-day max; 1 write/s per key ([R2 pricing](https://developers.cloudflare.com/r2/pricing/), [presigned](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)) |
| Users, doc index, shares, releases | D1 | 10 GB per DB, 2 MB max row; 30-day Time Travel on Paid ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/)) |
| Live annotation sync | Durable Objects (SQLite, WebSocket Hibernation) | Incoming WS messages billed 20:1; hibernation drops Cloudflare's 100-object example from ~$412.50 to ~$12.50 ([DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)) |
| Light server ops (merge, split, flatten, generate) | Worker running `lamina-wasm` | **128 MB memory**, 64 MiB script, 30 s → 5 min CPU on Paid, 10 ms on Free; 100 MB body on Free/Pro ([limits](https://developers.cloudflare.com/workers/platform/limits/)) |
| Multi-step jobs | Workflows + Queues | 1 MiB step result (blobs go to R2); 5 min CPU per step ([Workflows limits](https://developers.cloudflare.com/workflows/reference/limits/)) |
| OCR, Office↔PDF, Ghostscript | Containers (GA 2026-04-13) | Up to 4 vCPU/12 GiB; billed per 10 ms active CPU; not on Free ([Containers limits](https://developers.cloudflare.com/containers/platform-details/limits/), [pricing](https://developers.cloudflare.com/containers/pricing/)) |
| HTML→PDF | Browser Run (formerly Browser Rendering) | 10 browser-hours/month included, then $0.09/h ([pricing](https://developers.cloudflare.com/browser-rendering/pricing/)) |
| Flags, channel pointers | KV | Read-heavy only; writes $5/M after 1M ([pricing](https://developers.cloudflare.com/workers/platform/pricing/)) |

The table shows where the line falls. The Rust core's WASM runs comfortably inside a Worker for structural operations on modest files. But the **128 MB isolate** rules out large files, bulk rasterisation and OCR, and the **10 ms Free-tier CPU** means any server feature implies Workers Paid at $5/month minimum. Heavy feature groups route through Workflows to Containers: OCR in group H, Office conversion, and batch work in group K ([06 §2](../pdf/06-feature-inventory.md)). Uploads go browser → presigned PUT on R2's S3 endpoint → D1 row, with R2 lifecycle rules expiring processing files (for example after 24 h). Users who need a hard privacy guarantee get client-side encryption. That forgoes server processing for those files, a trade-off the UI must state.

Desktop distribution uses the same platform. Tauri's updater requires signatures and supports either a static `latest.json` or a **dynamic endpoint that returns 204 or 200 JSON**, with `{{target}}`, `{{arch}}` and `{{current_version}}` variables. It ships full bundles only, with no delta updates ([Tauri updater](https://v2.tauri.app/plugin/updater/)). CI uploads artifacts and `.sig` files to R2 under `releases/{version}/{target}-{arch}/`. A Worker at `updates.<domain>/{channel}/{{target}}/{{arch}}/{{current_version}}` reads a channel manifest. It hashes the install ID into a rollout percentage, honours kill switches, and returns a URL on R2's public custom domain. Presigned URLs cannot use custom domains, and the S3 endpoint requires auth ([electron-builder R2Options](https://www.electron.build/docs/api/builder-util-runtime.Interface.R2Options)).

```
 GitHub Actions (tauri-action matrix) ──► R2: releases/{ver}/{target}-{arch}/{bundle,.sig}
                                     └──► R2/KV: channels/{stable|beta|nightly}/manifest.json
 Desktop app ──GET /{channel}/{target}/{arch}/{current}──► Worker "updates"
        ▲                                                   │ rollout %, kill switch, 60 s cache
        └──── 204 No Content | 200 {version,url,signature} ◄┘
        └──── download from downloads.<domain> (R2 custom domain, free egress) ──► verify sig ──► install
```

The updater's private key is a single point of failure: losing it "blocks updates for existing users" ([Tauri updater](https://v2.tauri.app/plugin/updater/)), so key custody belongs in an ADR. At small-to-medium scale the whole footprint is Workers Paid at $5, plus about $1.35/month per 100 GB of R2, plus metered Container and Browser Run usage. The one dated cost change is Workers Logs moving to "Cloudflare Observability pricing" on **1 December 2026** ([pricing](https://developers.cloudflare.com/workers/platform/pricing/)).

## The repository is Cargo, pnpm and a task runner, released through OIDC and gated by a PDF corpus

> **Editor's note (2026-10-28):** after this report was written, the project's [code-organization guide](../../guidelines/code-organization.md) chose a single task entry point, `cargo xtask` under `tools/xtask/`, instead of `just`. Read "just" below as "xtask"; the layout tree has been updated.

The leading Rust+JS projects converge on one plain layout. Oxc, Biome, Rolldown and Tauri all use a root Cargo workspace (`crates/`), a pnpm workspace (`packages/`, `apps/`) and a `justfile` or `xtask`, and none of them puts Turborepo, Nx or moon at the root ([Oxc](https://github.com/oxc-project/oxc), [Biome](https://github.com/biomejs/biome), [Rolldown](https://github.com/rolldown/rolldown), [Tauri](https://github.com/tauri-apps/tauri)). Turborepo's Cargo support is behind an experimental flag with caching off by default ([Turborepo Rust](https://turborepo.dev/docs/guides/tools/rust)). Lamina should copy the convergent layout and add Turborepo only if TS-side caching becomes painful:

```
crates/   lamina-syntax  lamina-cos  lamina-model  lamina-ops  lamina-save  lamina-build
          lamina-text    lamina-render (+ pdfium, hayro adapters behind features)
          lamina         (façade crate re-exporting the public API)
          lamina-wasm    (wasm-bindgen cdylib)   lamina-ffi (UniFFI, later)   lamina-cli
packages/ pdf            (@lamina/pdf: TS API over lamina-wasm, ESM-only)
          wasm           (@lamina/wasm: generated glue + .wasm, build output, gitignored)
          render-pdfium  (@lamina/render-pdfium: optional, ships pdfium.wasm)
          render-hayro   (@lamina/render-hayro: optional, pure-Rust renderer as its own .wasm)
          viewer         (@lamina/viewer: framework-free viewer core: virtualiser, layers, RPC)
          ui             (React chrome + Platform adapter interface)
apps/     web            (Worker + static assets; optional api/ routes, DOs, Workflows)
          desktop        (Tauri; src-tauri depends on crates/* by path, no WASM)
          updates        (update/download Worker)
fixtures/ (small golden PDFs in git)    corpus/ (large corpus in R2, pinned by hash)
fuzz/     (cargo-fuzz, OSS-Fuzz layout)  tools/xtask/  deny.toml  rust-toolchain.toml
```

The **package design** follows from size and runtime reach. The `.wasm` binary cannot be tree-shaken, so rendering lives in a separate optional package. `@lamina/pdf` stays near the spike's 74 KB gzipped core plus generation, while `@lamina/render-pdfium` carries PDFium's megabytes only for those who want them (an inference: the repo notes found no 2026 source on wasm-bindgen tree-shaking). The generator API mirrors krilla's write-once builder (`Document → page → surface → finish`) ([krilla](https://docs.rs/krilla/latest/krilla/)), but `finish()` returns a Lamina `Document` rather than bytes. A generated file can then be edited and saved through the same `Document::open` / `transact` / `save({mode})` API that the apps use, which is how "generate first, read/edit later" avoids a second API. In TypeScript, the library is **synchronous after an async `init()`**: WASM calls are synchronous, and only the viewer needs a worker. `init()` accepts a URL or a precompiled `WebAssembly.Module`, which Cloudflare Workers require, and the package exposes `browser`, `workerd`, `node` and `default` export conditions, validated by publint and `attw --pack` (practice from the repo notes, partly unverified). The build drives `cargo build --target wasm32-unknown-unknown` → `wasm-bindgen` → `wasm-opt -Oz` directly from `just`. The `rustwasm` org was archived in 2025, and wasm-bindgen moved to a new org that is actively released ([Inside Rust](https://blog.rust-lang.org/inside-rust/2025/07/21/sunsetting-the-rustwasm-github-org)). Data structs get TypeScript types via upstream **tsify**, and live handles (`Document`, `Page`) stay `#[wasm_bindgen]` classes, as Bitwarden's SDK guidance recommends ([Bitwarden](https://contributing.bitwarden.com/architecture/sdk/web/interoperability)). napi-rs v3's WASM output targets only `wasm32-wasip1-threads` and needs COOP/COEP in browsers ([napi-rs](https://napi.rs/docs/concepts/webassembly)). That makes it a later Node-native option, not the browser path. WASI 0.3 was ratified in June 2026 but jco support is still landing ([wasi.dev](https://wasi.dev/releases/wasi-p3)), so the Component Model waits until 2027.

**Releases use OIDC trusted publishing on both registries.** npm's reached GA on 2025-07-31 with automatic provenance ([GitHub changelog](https://github.blog/changelog/2025-07-31-npm-trusted-publishing-with-oidc-is-generally-available/)). crates.io's added a per-crate "trusted publishing only" mode in January 2026, after a mandatory manual first publish ([crates.io update](https://blog.rust-lang.org/2026/01/21/crates-io-development-update)). Lamina should reserve names early, then switch every crate to trusted-only. Because `@lamina/wasm` is tightly coupled to the core crates ("lamina-core" in this report means the set `lamina-syntax` … `lamina-text`, published through the `lamina` façade), **lockstep versioning** of the core crates and the WASM/TS packages, driven by Changesets with a script that syncs `Cargo.toml`, is simpler than independent Changesets plus release-plz streams. Apps version independently. Gates are cargo-semver-checks, attw and publint. Desktop binaries and `.wasm` get GitHub artifact attestations alongside Tauri's own updater signature.

**Testing is where the PDF domain diverges from ordinary web projects.** The spike's strongest finding was methodological: shared fixtures, byte-identical goldens, a pypdf-derived corpus and differential fuzzing caught bugs single-implementation tests missed. The first differential run disagreed on 12% of damaged files purely through unwritten tolerance policy ([07 §4](../pdf/07-spike-rust-and-typescript.md)). CI therefore has four tiers. The **PR fast lane** runs fmt, clippy `-D warnings`, nextest, a wasm32 build with a size budget, TS typecheck/lint/Vitest, publint/attw and cargo-deny. The **PR full lane** adds the three-OS matrix, golden render tests (rasterise, compare against committed PNGs with perceptual thresholds, plus a pdf.js-style `--masterMode` to refresh goldens ([DeepWiki pdf.js testing](https://deepwiki.com/mozilla/pdf.js/6.2-testing-infrastructure))) and Playwright screenshots of `apps/web`. **Nightly** runs differential tests against pdf.js, PDFium, qpdf and pypdf over the R2-hosted corpus, hayro-vs-PDFium render diffs, extended fuzzing, veraPDF validation via its Docker image ([verapdf/cli](https://hub.docker.com/r/verapdf/cli)) and benchmarks. **Release** runs tauri-action ([Tauri pipelines](https://v2.tauri.app/distribute/pipelines/github)), OIDC publishing and the R2 upload. Fuzz targets use the layout OSS-Fuzz expects for Rust ([OSS-Fuzz](https://google.github.io/oss-fuzz//getting-started/new-project-guide/rust-lang/)). The capability matrix from chapter 06, each of the ~180 operations tagged unsupported/read/write/round-trip, becomes a generated test-backed feature table that the apps also use to enable UI ([06 §10](../pdf/06-feature-inventory.md)).

## Decisions, alternatives, risks and open questions

### Each decision has a credible alternative and a known price

| Decision | Recommended | Main alternatives | Why the recommendation wins / what it costs |
|---|---|---|---|
| Core | Rust, MIT OR Apache-2.0, bytes-in/bytes-out | TS core; wrap C/C++ engines | Spike: safety guarantees with less review, 74 KB WASM, one core for all shells. Costs a higher contributor barrier ([05](../pdf/05-creating-pdfs-from-code.md), [07](../pdf/07-spike-rust-and-typescript.md)) |
| Renderer (apps) | `RenderBackend` trait; PDFium default (native + WASM); hayro as oracle and future default | pdf.js; hayro-only; MuPDF (AGPL, excluded) | Fidelity, forms and annotations now under Apache-2.0. Costs ~4.6 MB WASM, C++ attack surface, and the two-parsers problem |
| Renderer (packages) | None by default; hayro or PDFium as opt-in packages | Bundle PDFium | Keeps `@lamina/pdf` small. Users who need rasterisation opt in |
| Desktop shell | Tauri 2, direct distribution | Electron; native UIs; Slint/egui/GPUI | Native Rust core and shared UI. Costs Linux WebKitGTK fragility and DIY printing |
| Desktop data path | Native core in a sandboxed child process; tiles via Channel or `lamina://` | WASM inside the webview (identical to web) | mmap, no 4 GB cap, threads. Costs IPC design. The WASM path is kept for parity tests |
| Web chrome | React 19 + Compiler; framework-free viewer core | Solid 2 (rc), Svelte 5, Lit | Contributor pool and a11y primitives. Costs runtime size, mitigated by keeping the hot path out of React |
| Worker boundary | Typed custom RPC; single-thread WASM baseline, threaded when isolated | Comlink; mandatory COOP/COEP | Cancellation and priority control. Avoids breaking OAuth and embeds |
| Document model | Lazy COS overlay + typed views + op log | Eager graph (lopdf); pdf.js AnnotationStorage | Large files in wasm32; automatic dirty tracking; a single op stream for undo and sync |
| Save | Planner with `SaveConstraint` (Free / AppendOnly / RequiresRewrite) | Caller-chosen mode (LibPDF) | Makes signature-breaking and redaction-leaking saves impossible by default |
| Collaboration | Server-authoritative records via one DO per document; LWW per property | Yjs/Loro/Automerge CRDT | Matches Figma, tldraw and Nutrient. CRDT only if offline or P2P is required |
| Web hosting | Workers static assets + optional `/api` Worker | Pages | Pages is de-emphasised. Static requests are free |
| Heavy processing | Workflows → Containers; light ops in Worker WASM | Everything in Workers; third-party APIs | 128 MB Worker memory; Containers GA with active-CPU billing |
| Updates | Dynamic update Worker + R2 + channel manifests | Static `latest.json`; GitHub Releases | Staged rollout and kill switch with no republish. Full bundles only |
| Repo | Cargo + pnpm + just; crates/packages/apps | Turborepo/Nx/moon-centric | Matches Oxc, Biome, Rolldown and Tauri |
| Versioning | Lockstep core + WASM/TS via Changesets; apps independent | Changesets + release-plz separately | One version for one ABI. Independent streams fit later |

### Six risks deserve owners

| Risk | Likelihood / impact | Mitigation |
|---|---|---|
| **Two parsers** (Lamina core + PDFium) disagree on malformed files, or re-render after content edits is slow | High / High for phase 4 editing | Overlay-first rendering for annots, fields and page ops; incremental re-render of touched pages; nightly differential corpus; push hayro to parity |
| **Linux WebKitGTK** canvas and compositing failures | Medium-high / Medium | No GPU dependency; renderer switch; documented env workarounds; Electron-on-Linux fallback |
| **wasm32 4 GB ceiling** and Safari canvas/memory caps on huge files | Medium / Medium | `ByteSource` streaming, OPFS cache, tile caps; desktop handles giants natively |
| **PDFium supply chain** (prebuilt WASM, `pdfium-render` single maintainer, memory bugs like the 0.9.4 double-frees) | Medium / High | Pin and reproduce builds; run in worker or child process; keep the trait so the backend can be swapped |
| **Signing identities and keys** (Windows Artifact Signing eligibility, Apple notarisation, updater key loss) | Medium / High | Organisational legal entity early; HSM or secret-manager custody; key-rotation runbook ADR |
| **Scope**: ~180 operations across three products overwhelms a small team | High / High | Capability matrix as the roadmap; phases from [06 §9](../pdf/06-feature-inventory.md); packages ship value before the editor |

### Open questions the research could not close

Several questions remain open. The notes found **no neutral 2026 fidelity benchmark**, so "when does hayro become default?" needs Lamina's own pass-rate threshold. No source measured **Channel vs `ipc::Response` vs custom-scheme throughput** on all three webviews, or confirmed that WKWebView and WebKitGTK honour COOP/COEP on Tauri's custom protocol, so a desktop spike must measure both. **Printing** on Tauri lacks a sourced answer. Whether **krilla can write into an existing object graph** decides whether Lamina wraps it for generation or builds its own builder over `lamina-cos` ([05 §8.7](../pdf/05-creating-pdfs-from-code.md)). **End-user auth** for the optional server tier (Better Auth/Auth.js on D1 vs hosted vendors) was not researched with sources. **Workers AI OCR** model availability and Container cold-start times are undocumented in the pages read, so OCR stays on Tesseract/OCRmyPDF in Containers until measured. Finally, there are product questions only the team can answer: which ships first, the `@lamina/pdf` generator or the web reader; whether a hosted Lamina service is a goal or just a reference deployment for forks; package and domain naming; and whether the Mac App Store, Flathub and mobile (Tauri mobile vs UniFFI to native UIs) are in scope.

## Conclusion

This research mostly confirms the "one Rust core" thesis. It also exposes what that thesis hides: the core and the renderer are different decisions with different timelines. Treating rendering as a swappable backend, PDFium today and hayro when the corpus proves it, lets Lamina ship a credible reader without betting the editor on a 0.x renderer, while keeping the long-term pure-Rust goal intact. The cost is a two-parsers seam that has to be engineered deliberately rather than discovered in phase 4. The other non-obvious conclusion is that **the save planner, not the UI, is where an editor's correctness lives**. Signatures, redaction and incremental updates impose ordering rules that must be encoded in the core's type system, or every shell will re-learn them as bugs.

The sequencing implication is that the packages should ship first. `@lamina/pdf` and the `lamina` crate exercise the COS layer, op log, save planner, test corpus and release pipeline with no UI risk and almost no hosting cost. The web reader is then a thin shell over a proven engine, and the desktop app is a second thin shell over the same crates. Cloudflare's job is to keep that whole stack nearly free to run and to make a privacy-first default the cheapest option.
