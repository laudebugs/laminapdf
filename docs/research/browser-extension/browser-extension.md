# Bundle Lamina's reader into every browser

Lamina should build the extension, and it should ship the whole WASM reader inside the package. A thin redirect to app.laminapdf.com is the wrong shape. The decisive reason is technical. An extension page that holds host permissions can fetch cross-origin PDFs whatever their CORS headers say ([Chrome docs](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests)). That removes the web reader's biggest limitation and turns Lamina from "opens PDFs on CORS-friendly hosts" into "opens the PDFs you click". What the extension can do differs a lot by browser. Chromium 128+ can take over any response served as `application/pdf` using declarativeNetRequest response-header rules. Firefox can do the same with blocking `webRequest`, which it keeps in Manifest V3. Safari has neither mechanism, so it can only catch URLs that look like `.pdf`, plus whatever the user opens by button or context menu. The market opening is real but narrow. Adobe Acrobat has **351M** Chrome users and well-documented takeover bugs. The only open-source local viewer with scale, Mozilla's PDF.js extension, has **1M users, no update since October 2024, and opt-out telemetry**. Newer "private, local" entrants have barely any users. The plan is to ship to Chromium first (one Chrome Web Store listing also covers Edge's engine, Brave, Vivaldi and Opera), then Firefox (where the AMO reproducible-build review is the main cost), then Safari as a button-first companion. Compete on verifiable privacy and on reliability, not on annotation features, which Chrome now gives away free.

## The extension fixes the web reader's CORS wall, but each engine intercepts PDFs differently

The web reader at app.laminapdf.com opens remote files through `#url=` and HTTP Range requests. It fails whenever the host sends no CORS headers, which describes most of the web. Inside an extension the same loader runs from an extension page, and Chrome states that extension code "can talk to remote servers outside of its origin, as long as the extension requests host permissions" ([Chrome docs](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests)). Content scripts **do not** get this exemption, so the fetch has to happen in the viewer page or the background context, never in a script injected into a website. A redirect-only extension keeps the CORS problem, because only extension contexts get the exemption. It also cannot pass `file://` PDFs to a web origin, and it routes every PDF the user opens through a Lamina-hosted page. Its real advantages are a tiny package and reader updates that skip store review. That makes it a sensible fallback, but not the product ([Chrome docs](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests); [WECG #381](https://github.com/w3c/webextensions/issues/381)).

The reader's engine moves into an extension with little friction. The MV3 content security policy allows `script-src 'self' 'wasm-unsafe-eval'`. That keyword is required for WASM in Chrome, Firefox and Safari, and pdf.js ships exactly this policy in its own MV3 extension ([MDN](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/content_security_policy); [pdf.js manifest](https://github.com/mozilla/pdf.js/blob/master/extensions/chromium/manifest.json)). A Chrome developer-relations reply confirms that such extensions can be published to the Web Store ([chromium-extensions](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/sJiaTnFMLHQ)). Two constraints follow. First, Vite must emit the worker and the WASM as real files in the package, because blob and data URLs are blocked under this CSP. Second, Lamina should keep its **single-threaded WASM build**. Chrome extensions can opt into cross-origin isolation and SharedArrayBuffer through manifest keys ([Chrome docs](https://developer.chrome.com/docs/extensions/develop/concepts/cross-origin-isolation)), but the Firefox bug for the same feature was reopened and is still unresolved as of July 2026 ([Bugzilla 1673477](https://bugzilla.mozilla.org/show_bug.cgi?id=1673477)).

The background context differs by browser. Chrome requires a service worker, Firefox does not support `background.service_worker` and uses event-page `scripts`, and Safari accepts both. One manifest can declare both keys, and Chrome 121+ and Firefox 121+ each pick the one they understand ([BCD](https://github.com/mdn/browser-compat-data/blob/main/webextensions/manifest/background.json); [Mozilla Add-ons blog](https://blog.mozilla.org/addons/2024/03/13/manifest-v3-manifest-v2-march-2024-update/)). MV3 is the only sensible target. Chrome stopped running MV2 in Chrome 139 and removed the last MV2 items from the Web Store on **August 31, 2026** ([Chrome timeline](https://developer.chrome.com/docs/extensions/develop/migrate/mv2-deprecation-timeline)). From **Chrome 148**, every extension API is also exposed under the promise-based `browser` namespace ([Chrome docs](https://developer.chrome.com/docs/extensions/develop/concepts/browser-namespace)). For that reason Mozilla archived `webextension-polyfill` on 2026-07-30 ([README](https://github.com/mozilla/webextension-polyfill)). Lamina can therefore write plain `browser.*` code and fall back to `globalThis.browser ?? chrome` for Chromium forks that lag upstream.

## Copy pdf.js's takeover rules, then fix the failures users already hate

In Chromium, the template to copy is Mozilla's own pdf.js extension, whose source is public ([pdfHandler.js](https://github.com/mozilla/pdf.js/blob/master/extensions/chromium/pdfHandler.js)). It registers **dynamic** DNR rules once per browser session, guarded by a `storage.session` flag, because `runtime.onInstalled` does not always fire. The rules are checked in priority order. An allow rule honours a `download` escape-hatch query parameter. Requests whose `content-type` is `application/pdf` redirect to the viewer, except POST requests, because "the original response to POST requests is unavailable". `.pdf` URLs and `Content-Disposition` filenames served as `application/octet-stream` also redirect. A `Content-Disposition: attachment` header is respected inside iframes and overridden in the top frame, "since most often users want to view a PDF, and servers are often misconfigured". A special case keeps Google Drive downloads working. Lamina should adopt this rule set nearly verbatim, with a `lamina.action=download` escape hatch.

pdf.js also carries one non-obvious safeguard. Chrome 121–127 accept the `responseHeaders` condition but **silently ignore it**, so a naive rule would redirect every request on the web ([BCD](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/declarativeNetRequest.json); [crbug 347186592](https://crbug.com/347186592)). pdf.js probes the condition with session rules first and falls back to a content script if the probe fails. Lamina needs the same probe for Chromium forks that lag behind upstream. DNR has two more constraints. A redirect target set by `extensionPath` must be web-accessible. And because DNR cannot URL-encode the captured URL, pdf.js appends it raw with `regexSubstitution` ([Chrome DNR reference](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest)).

Firefox works differently, and in one respect better. Firefox has **no plan to drop blocking webRequest** and promises 12 months' notice if MV2 ever goes ([Mozilla Add-ons blog](https://blog.mozilla.org/addons/2024/03/13/manifest-v3-manifest-v2-march-2024-update/)). An `onHeadersReceived` listener can return `redirectUrl` to the extension viewer ([Bugzilla 1224581](https://bugzilla.mozilla.org/show_bug.cgi?id=1224581)). Since Firefox 60, extensions cannot touch PDFs that Firefox's built-in pdf.js has already rendered, so interception at the network layer is the only design that works there ([Bugzilla 1454760](https://bugzilla.mozilla.org/show_bug.cgi?id=1454760)). The redirect should happen before pdf.js's stream converter sees the body, which would let Lamina win without the user changing `pdfjs.disabled`. No primary document confirms that ordering, so it is the first thing to prototype. Safari is the outlier. Its bug for matching on response headers has been NEW since 2024 ([WebKit 275158](https://bugs.webkit.org/show_bug.cgi?id=275158)). A DNR redirect to a `safari-web-extension://` URL fails unless it uses `extensionPath`, and `extensionPath` cannot carry the original URL ([WECG #381](https://github.com/w3c/webextensions/issues/381)). Turning off Safari content blockers also turns off extension DNR ([WebKit 303800](https://bugs.webkit.org/show_bug.cgi?id=303800)), and Safari 26.0 shipped a redirect regression ([Apple forums](https://developer.apple.com/forums/thread/803502)). On Safari the reliable entry points are an "Open in Lamina" toolbar action and a link context menu. Opportunistic catching of `.pdf` URLs comes second.

The competitive opportunity lies in the failure cases. Adobe's extension, with 351M users, has documented problems. It ignores `#page=` deep links ([Adobe Community](https://community.adobe.com/t5/adobe-acrobat-online-discussions/bug-report-acrobat-chrome-extension-does-not-respect-page-specific-pdf-links/td-p/13223193)). It fetches the PDF twice, which breaks one-time download URLs ([Adobe Community](https://community.adobe.com/t5/adobe-acrobat-online-discussions/adobe-acrobat-chrome-extension-doing-multiple-calls/m-p/15480238)). It renders blank pages and crashes on large files ([Adobe Community](https://community.adobe.com/t5/adobe-acrobat-online-discussions/problem-with-adobe-chrome-extension/td-p/15409221/highlight/true)). Lamina should honour `#page=` and other open parameters, stream large files with Range requests instead of loading them whole, and show a one-click "Open in browser viewer" on every page. One caveat is honest and important. Chrome's DNR documentation says that by the time a response-header rule fires, "the request has already been sent to the server", and the redirect issues a new request ([Chrome DNR reference](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest)). **In Chromium, Lamina will also re-fetch every intercepted PDF**, so one-time URLs and some cookie-gated documents will hit the same wall Adobe's do. Only Firefox's `filterResponseData` can hand the original bytes to the viewer ([BCD](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/webRequest.json)). The mitigation is honest fallbacks: detect a failed re-fetch and send the user back to the native viewer. Lamina should not claim to have solved the problem.

Two more entry points matter. Local `file://` PDFs are invisible to DNR unless the user turns on "Allow access to file URLs". pdf.js handles this with `webNavigation.onBeforeNavigate` plus a prompt that deep-links to the extension's settings ([pdfHandler.js](https://github.com/mozilla/pdf.js/blob/master/extensions/chromium/pdfHandler.js)). That costs a "Read your browsing history" warning ([Chrome permissions list](https://developer.chrome.com/docs/extensions/reference/permissions-list)), so v1 should rely on the viewer's own file picker and drag-and-drop instead. PDFs embedded with `<embed>` or `<object>` need a content script that detects them and swaps in an iframe ([contentscript.js](https://github.com/mozilla/pdf.js/blob/master/extensions/chromium/contentscript.js)). That is a phase-two feature.

## Ask for nothing at install, and make "no data collected" provable

Permission design decides both conversion and trust. In Chrome, `declarativeNetRequestWithHostAccess`, `contextMenus`, `storage` and `activeTab` produce **no install warning**. Plain `declarativeNetRequest` warns "Block content on any page", and `tabs` and `webNavigation` each warn "Read your browsing history" ([Chrome permissions list](https://developer.chrome.com/docs/extensions/reference/permissions-list)). Full automatic takeover still needs host access to every site, which carries Chrome's broadest warning. If an update later adds a permission that carries a warning, Chrome **disables the extension until the user accepts** it ([Chrome permission warnings](https://developer.chrome.com/docs/extensions/develop/concepts/permission-warnings)). The install-time permission set therefore has to be right in v1. No rigorous study measures how much the all-sites warning cuts installs. The figures that circulate come from unsourced blogs, and this report does not rely on them.

The recommended design installs with only warning-free permissions and declares `<all_urls>` under `optional_host_permissions`. Onboarding then opens on a single, clearly explained choice, "Open PDFs in Lamina automatically", whose click calls `permissions.request`. Because `declarativeNetRequestWithHostAccess` applies rules only where the extension has host access, the DNR rules activate once the grant is given. A user who declines still gets the toolbar button, the context menu and the file picker, all running on `activeTab`. This matches where every browser is heading. Firefox 127+ shows MV3 host permissions at install, but users can revoke them at any time, and Mozilla tells developers to check with `permissions.contains` ([Mozilla Add-ons blog](https://blog.mozilla.org/addons/2024/05/14/manifest-v3-updates/)). Safari grants access per site, with "Allow for One Day", "Always Allow on This Website" and "Always Allow on Every Website" options ([Apple](https://developer.apple.com/documentation/safariservices/managing-safari-web-extension-permissions)). The design rule that follows holds in every browser: when access is missing, Lamina never breaks the page. It shows a "PDF detected" badge and opens the document on the user's click. Over-broad permissions also carry a reputational cost in this category. The malicious PDF Toolbox extension asked for all-sites access "to scan every open tab for PDFs" when `activeTab` would have been enough ([Palant](https://palant.info/2023/05/16/malicious-code-in-pdf-toolbox-extension/)).

The privacy declarations line up with Lamina's existing promise. Firefox has required `browser_specific_settings.gecko.data_collection_permissions` for every new AMO submission since **November 3, 2025**. Lamina declares `"required": ["none"]`, and the install prompt then shows that no data is collected ([Extension Workshop](https://extensionworkshop.com/documentation/develop/firefox-builtin-data-consent/)). Any future opt-in crash reporting must go under `optional`, as `technicalAndInteraction`. The Chrome Web Store requires a Limited Use statement and a privacy policy ([CWS Limited Use](https://developer.chrome.com/docs/webstore/program-policies/limited-use)). Edge's Partner Center asks for a single-purpose statement, a justification for each permission and a remote-code declaration ([Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-edge/extensions/publish/publish-extension)). "View and annotate PDF files locally" fits all of them.

Declarations are cheap, though, and the "local-only" label is already crowded with unverifiable claims. Lamina should make its claim checkable. The viewer page can carry a strict `connect-src`, and the web reader's request indicator should show its count inside the extension too. Releases can publish deterministic builds with SHA-256 hashes and provenance attestations, plus a "verify" guide for diffing the store package against the GitHub release. The store re-signature changes only the CRX header, not the zip contents. Security deserves the same rigour as privacy, because the likeliest attack is on the publisher, not the code. In December 2024 a phishing email led a Cyberhaven employee to grant a malicious OAuth app access to the company's Chrome Web Store items. A poisoned update then reached about **400k users** in roughly 25 hours, and the wider campaign hit as many as 35 extensions ([Island.io](https://www.island.io/info/cyberhaven-and-extension-takeover-incident); [Reco.ai](https://reco.ai/blog/cyberhaven-supply-chain-attack-how-one-phishing-email-led-to-over-400-000-compromised-browsers); [BleepingComputer](https://bleepingcomputer.com/news/security/new-details-reveal-how-hackers-hijacked-35-google-chrome-extensions)). Chrome's **verified CRX uploads** (May 2025) reject any upload not signed with the developer's registered private key, "even if the account or publishing workflow is compromised" ([Chrome blog](https://developer.chrome.com/blog/verified-uploads-cws)). Lamina should opt in from day one. It should also keep the signing key out of everyday CI secrets, for example behind a GitHub Environment that needs a human reviewer, keep the number of store admins small, and use a store contact address that is not public.

Enterprise deployment comes almost for free and is worth documenting early. Chrome and Edge `ExtensionSettings` support `force_installed`, `force_pinned` toolbar placement, `runtime_blocked_hosts`, and from Chrome 119 `file_url_navigation_allowed` ([Google Admin help](https://support.google.com/chrome/a/answer/9867568)). Firefox can pass admin settings to extensions through the `3rdparty` policy and `storage.managed` ([Mozilla policy templates](https://mozilla.github.io/policy-templates/)). No policy makes an extension the default PDF handler. `AlwaysOpenPdfExternally` only turns off the built-in viewer so that PDFs download ([Microsoft Learn](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-browser-policies/alwaysopenpdfexternally)). Admins should leave it unset and let the DNR redirect do the work. One problem remains open. Chrome's policy page describes no field that *grants* permissions ([Google Admin help](https://support.google.com/chrome/a/answer/9867568)), and Firefox admins are still asking how to auto-grant MV3 host access on forced installs ([Mozilla Discourse](https://discourse.mozilla.org/t/allowing-accessing-data-on-all-websites-for-group-policy-installations-with-manifest-v3/131351)). If optional host permissions stay ungranted on managed installs, the zero-warning design and fleet deployment pull against each other.

## WXT and one release workflow cover three stores; Safari and AMO review set the pace

**WXT** is the right build tool for a Vite and pnpm monorepo. It is Vite-based and actively released (v0.21.5, 2026-10-26, about 1.09M weekly npm downloads). It is the only framework examined that ships built-in multi-store `submit` and generates the Firefox sources zip. Plasmo has not released since May 2025, and CRXJS is a plugin without publishing support ([WXT](https://github.com/wxt-dev/wxt); [Plasmo](https://github.com/PlasmoHQ/plasmo); [WXT publishing](https://wxt.dev/guide/essentials/publishing)). The reader becomes an unlisted `viewer.html` entrypoint that imports the existing `apps/web` code as a workspace package. A background entrypoint owns the DNR rules, or the webRequest listener on Firefox. `wxt build -b chrome|firefox|safari|edge` produces each target, and Edge reuses the Chrome zip. Refactoring the SPA so its shell can host either the web app or the extension viewer is the main engineering task. The extension code itself is small.

| Firefox AMO | Free | `web-ext sign` uploads the package and its source | Reviewers **rebuild from source and require byte-identical output** on Ubuntu 24.04 **ARM64** by default ([Extension Workshop](https://extensionworkshop.com/documentation/publish/source-code-submission/)) |

The AMO requirement is the sleeper risk. Reviewers rebuild the package from the submitted source and require "no differences" ([Extension Workshop](https://extensionworkshop.com/documentation/publish/source-code-submission/)). For Lamina that means Rust-to-WASM output and Vite chunk hashes must be bit-reproducible across x86_64 CI and an ARM64 reviewer machine. PDFium compiled through a C++ toolchain is far harder to pin than pure-Rust hayro. A containerised build with a pinned `rust-toolchain.toml`, wasm-bindgen version and pnpm lockfile, documented in the source README, is mandatory. The same work produces the reproducible-build proof that the privacy story needs, so it pays off twice. Mozilla's updated Add-on Policies take effect on **December 1, 2026** and should be read before the first submission ([Add-on Policies](https://extensionworkshop.com/documentation/publish/add-on-policies/)).

The release pipeline extends Lamina's existing GitHub Actions setup. A release tag triggers one reproducible Linux build that emits `chrome.zip`, `firefox.zip` and `firefox-sources.zip`. `wxt submit` then pushes them to the CWS, Edge and AMO, and every first listing is created by hand ([WXT publishing](https://wxt.dev/guide/essentials/publishing)). A separate macOS job packages, archives and uploads the Safari app with an App Store Connect API key. Testing falls into three tiers. Playwright loads extensions only in its bundled Chromium, through a persistent context ([Playwright docs](https://playwright.dev/docs/chrome-extensions)), so the interception path gets a Chromium E2E suite. Firefox gets `web-ext lint` and a run, and Safari gets a manual TestFlight check. Most behaviour runs in the viewer, which is the existing SPA, so the web reader's current test suite covers it.

## Win on trust and reading quality, because annotation is now table stakes

The built-in viewers have closed the basic gap. Chrome 145 (February 2026) added highlights, notes and signatures, along with a "Save to Drive" push ([9to5Google](https://9to5google.com/2026/02/19/chrome-split-view-pdf/)). Firefox's pdf.js editor handles text, ink, highlights, images and signatures ([Mozilla SUMO](https://support.mozilla.org/kb/view-pdf-files-firefox)). Edge now renders PDFs with Adobe's engine, and its legacy engine was scheduled for retirement in early September 2026 ([PCWorld](https://www.pcworld.com/article/2692717/microsoft-confirms-plan-to-kill-its-legacy-pdf-reader-in-edge-soon.html); [MC1072406](https://mc.merill.net/message/MC1072406/compare/2025-11-14T21-39-36-033Z/2026-05-18T16-51-56-293Z)). Free annotation therefore wins nobody over. Three things are still missing everywhere, and Lamina can supply them. The first is a real dark or reflow reading mode. Chrome and Firefox lack one, Firefox removed `pdfjs.viewerCssTheme` in Fx121, and extensions cannot do better than colour inversion on Chrome's viewer ([DEV](https://dev.to/liuhao04/why-most-pdf-dark-mode-chrome-extensions-do-nothing-on-a-web-pdf-on5); [pdf.js PR #17293](https://github.com/mozilla/pdf.js/pull/17293)). The second is a viewer without a vendor's cloud funnel. Adobe's listing discloses that it collects location and user activity ([CWS](https://chromewebstore.google.com/detail/adobe-acrobat-pdf-edit-co/efaidnbmnnnibpcajpcglclefindmkaj)), Chrome steers users to Drive, and Edge to Acrobat. The third is **the same viewer, with the same keybindings, annotations and editor, in Chrome, Edge, Firefox and Safari**, which no built-in viewer can offer by design.

Trust is the sharpest wedge, because this category has a malware history. PDF Toolbox had **2M users** and a 4.2 rating while hiding a remote-code backdoor for a year. Its removal triggered a purge of about 32 extensions with **75M combined installs** ([Palant](https://palant.info/2023/05/16/malicious-code-in-pdf-toolbox-extension/); [BleepingComputer](https://www.bleepingcomputer.com/news/security/malicious-chrome-extensions-with-75m-installs-removed-from-web-store/?web_view=true)). On AMO, search-hijacking "converter" add-ons with 100K+ users still sit near the top of a "pdf" search ([AMO](https://addons.mozilla.org/en-US/firefox/search/?q=pdf&sort=users&type=extension)). Against that background, an MIT/Apache extension with no telemetry, a minimal install footprint, a reproducible build and verified uploads is a meaningful difference that most competitors cannot copy without abandoning their upload-and-upsell model. The PDF.js extension is the direct rival for this slot. It has 1M users without marketing, which shows that people want a non-Adobe default. But it has gone more than two years without an update and has shipped opt-out telemetry since version 1.5.285 ([CWS](https://chromewebstore.google.com/detail/pdf-viewer/oemmndcbldboiebfnladdacbdfmadadm)).

The strongest argument against building the extension is demand. "Private, local" entrants keep appearing and keep failing to gain traction. OpenPDF has **26 users** ([CWS](https://chromewebstore.google.com/detail/openpdf-free-private-edit/eblfbmkkoiphfocgnnknpgljnncglcek)), which suggests distribution matters more than features. Firefox is the weakest market, since pdf.js is built in and no viewer extension reaches AMO's top results. Safari's interception is degraded on every axis. Four store listings add permanent maintenance overhead. These points argue for sequencing and restraint, not for abandoning the idea. Lamina's advantage over the 26-user entrants is that the extension is not the whole product. It is a distribution channel for an existing reader and a planned editor. The extension also gives the web reader something it cannot get alone: the ability to open the PDFs people actually click.

## Conclusion

The research changes the framing. The extension is not a wrapper around the web reader. It is the only way that reader can open the open web's PDFs, because only an extension context escapes CORS. The same platform work, a reproducible WASM build, has to happen for AMO review anyway, and it also makes Lamina's privacy promise provable instead of merely stated. The real constraint is not WASM or packaging. It is that every engine intercepts PDFs differently, and that Chromium's redirect always re-fetches. Lamina should therefore treat graceful fallback to the native viewer as a core feature, not an edge case.

**Recommendation: build it, bundle the reader, and ship in four phases.**
