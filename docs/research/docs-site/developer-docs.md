# Correct examples beat clever docs sites

Developers judge documentation first on whether it is complete and correct, and second on whether it shows working code they can start from; site polish, interactivity and framework choice come well behind. Technical documentation is still the most-used learning resource in the Stack Overflow survey (**83.9 %** in 2024, **67.8 %** in 2025, on different questions), and in the studies that rank problems, missing, ambiguous, outdated and wrong content are the ones that make developers give up on an API, while code examples are both the most-wanted content and the content most often wrong. Hacker News says the same over eleven years: across 21,499 comments in 197 threads about docs, complaints about missing or outdated docs and requests for examples hold steady at about 2 % of comments each, and the sites people name as their favourites (Stripe, Django, PostgreSQL, MDN) are praised for copyable, working code, versions you can switch to, and guides that explain the "why" as well as the reference. For Lamina PDF, this means the docs site is already on the right foundations: tested examples, page pictures of every result, a small runner of its own, Markdown twins for agents, and Starlight, which ships about 6 KB of script per page against 385–710 KB for the React-based alternatives. The redesign should **stay on Starlight**, keep the story order for first-time readers, and spend its effort on gaps in content and in the evidence the site shows: CLI transcripts that nothing checks, no guide for reading and extracting from code, no Rust or CLI first-run path, results hidden behind a tab, and recipes grouped by page type rather than by task. Every number below names its source; HN keyword counts carry the precision the research measured for them, and vendor claims and opinions are labelled.

## Docs stay the first stop, but trust now decides whether readers stay

Documentation is the resource developers use most, and AI is the rival growing fastest. In the 2024 Stack Overflow survey, **83.9 %** of 48,822 respondents named technical documentation as an online resource for learning to code, ahead of Stack Overflow itself at 80.3 % and AI at 37 %; among those who say where their documentation comes from, **90.3 %** use API and SDK documents (40,602 responses) ([SO 2024](https://survey.stackoverflow.co/2024/developer-profile)). The 2025 survey asked a broader question ("How did you learn to code in the past year?") and found documentation still first at **67.8 %**, with AI tools at 44 %; the two figures come from different questions, so the drop from 84 % to 68 % is not a decline ([SO 2025](https://survey.stackoverflow.co/2025/developers)). For learning to code *for AI*, AI tools already lead documentation, 52.5 % to 42.5 % ([SO 2025](https://survey.stackoverflow.co/2025/developers)).

The AI figures matter for a docs site because of what follows them. **84 %** of respondents use or plan to use AI tools, but **46 %** distrust their accuracy against 33 % who trust it, **66 %** name "AI solutions that are almost right, but not quite" as their top frustration, and **75.3 %** would still ask a person "when I don't trust AI's answers" ([SO 2025, AI](https://survey.stackoverflow.co/2025/ai)). Hacker News moved the same way: comments naming AI went from **0.2 %** of 2015–2022 comments to **8.7 %** of 2023–2026 ones, and 29 of the 90 docs threads since 2023 are about AI, agents or llms.txt ([themes_output.txt](../../../tools/hn-research/developer-docs/data/themes_output.txt)). The tone there is distrust of doc bots ("Docs are reliably fixable, so with enough effort they will converge to correctness. Doc bots are not and will not." — [HN](https://news.ycombinator.com/item?id=44509871)) and agreement that "making the docs AI-friendly essentially just ends up being what good documentation is in the first place" ([HN](https://news.ycombinator.com/item?id=44311346)). The rule that counts distrust and hallucination comments found **100 comments in 32 threads**, about 6 in 8 of them on theme when sampled.

The inference is that exact, versioned and tested statements are worth more now, not less: they are what readers check an "almost right" AI answer against, and what coding agents read. Older survey evidence points the same way. GitHub's 2017 open-source survey found that "**incomplete or outdated documentation is a pervasive problem, observed by 93 % of respondents**" ([GitHub 2017](https://opensourcesurvey.org/2017/)), and Postman's 2020 survey of over 13,500 people reportedly put lack of documentation as the top obstacle to consuming APIs at **54.3 %** — a figure I could only confirm through secondary coverage that quotes Postman's report, not on Postman's own page ([HackerNoon](https://hackernoon.com/54percent-of-developers-cite-lack-of-documentation-as-the-top-obstacle-to-consuming-apis-2v4w3e30)). DORA links documentation quality to large gains from engineering practices (for example, trunk-based development lifts organisational performance by 36 % with below-average docs against 1,525 % with above-average ones), but DORA measures internal team documentation, so it supports "quality matters" rather than any design choice for a public site ([DORA](https://dora.dev/capabilities/documentation-quality/)).

## Wrong, missing and unexplained content is what makes developers leave

The academic studies agree on what goes wrong, and it is content, not presentation. Robillard and DeLine surveyed Microsoft developers (80 answered the first survey, 334 the follow-up) and found learning resources (documentation and examples) the largest category of obstacles, named by **50 of 80** respondents, with documentation obstacles reported as the most severe; they list documentation of intent, code examples, and APIs matched to scenarios as the design factors that matter ([Robillard & DeLine 2011](https://www.cs.mcgill.ca/~martin/papers/ese2011.pdf)). Uddin and Robillard asked IBM developers (69 and then 254 respondents) about ten documentation problems: six were rated a "Blocker" ("I could not get past it and picked another API") at least once — incompleteness, ambiguity, obsoleteness, incorrectness, inconsistency and unexplained examples — and respondents "prioritized addressing five content-related problems over any presentation problem", with no difference between novices and experienced developers ([Uddin & Robillard 2015](https://www.cs.mcgill.ca/~martin/papers/ieeesw2015.pdf)). Aghajani and colleagues analysed 878 documentation artefacts from mailing lists, Stack Overflow, issues and pull requests and found that **code examples made up 50 % of correctness issues** where a documentation type was labelled, with installation guides next at 20 %; they recommend testing code examples like production code ([Aghajani et al. 2019](https://emadpres.github.io/pdfs/icse2019.pdf)).

Hacker News puts the same complaints in its own words. The rule for missing or outdated docs found **431 comments in 116 of the 197 threads**, with about 7 in 8 sampled matches on theme, and its share barely moved between periods (2.1 % before 2023, 1.9 % after) ([themes_output.txt](../../../tools/hn-research/developer-docs/data/themes_output.txt)). "Outdated documentation is worse than no documentation" ([HN](https://news.ycombinator.com/item?id=26012542)) and "Wrong documentation is even worse than no documentation" ([HN](https://news.ycombinator.com/item?id=35300979)) are typical. Requests for examples (a stricter rule needing a docs word and "example", "sample code" or "snippet" in one sentence) found **481 comments in 115 threads**, about 6 in 8 on theme, again flat over time ([strict_output.txt](../../../tools/hn-research/developer-docs/data/strict_output.txt)). The 2025 thread "Examples are the best documentation" mostly ended at "both": "worked examples and comprehensive references are mutually reinforcing kinds of documentation, meaning you want both" ([HN](https://news.ycombinator.com/item?id=45542456)). The fix that recurs is the one Lamina PDF already uses: "In rustdoc, documentation examples are compiled and run whenever you run your tests" ([HN](https://news.ycombinator.com/item?id=15562648)), and "link to actual code in the repo, in an examples directory, which gets compiled during every build" ([HN](https://news.ycombinator.com/item?id=25423296)).

Three further complaints are real but measured less firmly. Reference without guides or the "why" matched 170 comments in 75 threads, about half on theme ("documenting the 'what' but neglecting the 'why' or 'how'" — [HN](https://news.ycombinator.com/item?id=21377412)). Marketing in place of a plain statement of what the thing does matched 328 comments on a loose rule, about half on theme, and one 2026 thread, "I paid people to try and follow my README" (206 comments), found readers stuck on missing steps and on READMEs that never say what the software does ([HN](https://news.ycombinator.com/item?id=50042219)). Assumed knowledge and tone ("just", "simply") matched 644 comments but only about 3 in 8 on theme, so the firmer evidence is a single 2023 story, "Just Simply – Stop saying how simple things are in our docs", which drew 288 comments ([HN](https://news.ycombinator.com/item?id=35759449)). Lamina PDF's writing guideline already bans those words. Apple's developer docs are the standing bad example: six stories from 2019 to 2026 drew 1,258 comments, including "Apple Developer Documentation Is Missing" (389) ([HN](https://news.ycombinator.com/item?id=21376744)).

## Praised sites share working code, depth and reachable versions, not visual design

When HN commenters were asked directly for the best documentation they had read, the research hand-coded 215 top-level answers across five Ask HN threads (2018–2023). **Stripe led with 16**, then Django 9, PostgreSQL 8 and the Emacs manuals 8; old printed manuals as a group drew 18, which reads as a wish for complete, coherent, single-author documents ([nominations.txt](../../../tools/hn-research/developer-docs/data/nominations.txt)). The reasons are concrete mechanics. Stripe's "code samples (in 6-8 languages) are copy-paste ready using your own pre-populated credentials" ([HN](https://news.ycombinator.com/item?id=32794798)); Django has "no missing parts. Everything is documented and comes with examples, that work" ([HN](https://news.ycombinator.com/item?id=32795354)) and notes "what versions things changed" with a switch "at the click of a button" ([HN](https://news.ycombinator.com/item?id=33682987)); PostgreSQL keeps "docs for older versions available" ([HN](https://news.ycombinator.com/item?id=34821707)); hexdocs links each function to its source ([HN](https://news.ycombinator.com/item?id=32794714)). Among the 215 answers, a keyword count finds 39 mentioning examples, 21 concepts or overview, 11 search, 8 interactivity, 8 offline or built-in docs, 8 links to source, 7 versions and 6 single-page docs; "example" there includes "for example", so these are rough sizes. No such thread after February 2023 reached 50 comments, so newer sites are not represented.

The two sites most often studied for their design confirm the pattern and show what interactivity is for. Stripe's docs team says the docs should feel "like an application, not a user manual": the reader's own test key goes into code samples, content changes with the features the reader uses, and diagrams are interactive, all built on its own Markdoc language ([Stripe](https://stripe.dev/blog/markdoc)). Stripe publishes no usage figures for these features. react.dev launched in March 2023 with "over 600" editable sandboxes, challenges with solutions, and API pages split into *Reference* and *Usage*, some with Troubleshooting; writing the examples surfaced "mistakes in some of our own explanations, bugs in React, and even gaps in the React design" ([react.dev](https://react.dev/blog/2023/03/16/introducing-react-dev)).

How much interactivity matters to readers is the weakest-measured part of the evidence. Only **8 of 215** "best docs" answers cite interactivity, and the strict HN rule for playgrounds found 96 comments of which only about 3 in 8 were on theme ([strict_output.txt](../../../tools/hn-research/developer-docs/data/strict_output.txt)); where it is praised, it is on API sites ("Redis command docs are excellent and you can try the commands on the site itself!" — [HN](https://news.ycombinator.com/item?id=34821775)). The one observation study of how developers read API docs is more useful here. Meng, Steinhardt and Schubert eye-tracked 11 developers: they spent **about 49 % of task time in the docs**, the API reference drew the most time, examples and recipes **about 21 % each**, and **both "opportunistic" and "systematic" readers started from example code** ([Meng et al. 2019](https://mangold-international.com/resources/meng-et-al-how-developers-use-api-documentation-2019.pdf)). Eleven people is too few for statistics, as the authors say, but the finding fits everything above: what draws readers in is a working example they can copy and change, and a visible result. My opinion is that interactivity is a strong differentiator for a PDF library specifically, because no PDF library examined shows code and its rendered page side by side: pdf-lib sends readers to JSFiddle, and react-pdf and Nutrient keep separate playground pages ([pdf-lib](https://pdf-lib.js.org/), [Nutrient](https://unpkg.com/@nutrient-sdk/viewer@1.17.0/README.md)). That is an inference from a handful of sites, not a measurement.

Several site details recur in HN comments and cost little. Offline, plain-text, single-page or PDF access matched **252 comments in 92 threads**, about 7 in 8 on theme ("Lua's manual. One flat page with everything." — [HN](https://news.ycombinator.com/item?id=33684554); "Node.js because they propose a single page version and it makes search easier" — [HN](https://news.ycombinator.com/item?id=17406581)). Information locked in Discord or videos is disliked; "Discord is not documentation" alone drew 289 comments ([HN](https://news.ycombinator.com/item?id=36746154)). Error messages that link to docs pages draw delight because they are rare ("Every time I see an error in terminal with a link to documentation I'm delighted. And surprised." — [HN](https://news.ycombinator.com/item?id=33261836)), though only 8 comments in the adjacent error-message threads mention it. Complaints about slow, JavaScript-heavy sites and version mix-ups could not be counted (rule precision 2 in 8 or lower), dark mode appears in only 17 comments for and against, and copy buttons hardly come up; these rest on quotes, not counts.

Search deserves its own note. Meng's participants had no site search, fell back on in-page search, and failed because content was spread over pages; the authors recommend "a powerful search" ([Meng et al. 2019](https://mangold-international.com/resources/meng-et-al-how-developers-use-api-documentation-2019.pdf)). The same study found that a top-level split by page type ("Concepts", "Samples", "Recipes", "API reference") confused readers, who could not tell which category to open, and recommends organising "according to categories that reflect the functionality or content domain of the API rather than using categories that signal the type of information provided". That cuts partly against Diátaxis-style top-level splits; I found no peer-reviewed evaluation of Diátaxis, and on HN it drew only 3 of the 215 nominations.

## Lamina PDF's site already does the hard parts; its gaps are coverage and placement

The audit of `apps/docs` at `origin/main` 5abe81d (2026-11-11) found a site that meets most of the evidence above. There are 60 hand-written pages in a deliberate "docs as a story" sidebar (start here, runtime, concepts, create, read and edit, command line, production, recipes, troubleshooting, reference), plus 149 TypeDoc pages and 171 error-code pages ([sidebar.mjs](../../../apps/docs/plugins/sidebar.mjs); [current_docs_site.md](developer-docs/current_docs_site.md)). Every TypeScript and Rust block on guide and recipe pages comes from a tested example file, and the `Snippet` component refuses any other path at build time. Twenty pages show TypeScript and Rust side by side; each example has a Result tab with pictures of every page and a link to the PDF; six TypeScript examples on nine pages have "Edit and run" in a same-origin Web Worker; 13 inline-SVG diagrams follow the theme and share their text with the Markdown twins; every error code has a page with "What happened / Why / How to fix". The build writes a Markdown twin per page, `llms.txt` and `llms-full.txt`, and the packages ship a `docs/` folder for agents. Starlight's Pagefind search runs on the site's own origin, and the writing rules (a 50-word opening, 40-word sentences, banned words, no internal IDs) are checked by `cargo xtask check docs-prose`. These answer the top complaints in the studies and on HN — wrong examples, examples missing, the "why" missing, tone — better than most sites the research looked at.

The gaps are specific:

| Gap | What the audit found | Evidence it matters |
| --- | --- | --- |
| Unchecked CLI content | The 7 CLI pages' commands and outputs are hand-pasted `console` blocks; `sh` install blocks on 14 pages are unchecked, so "every code block is a tested example" is not quite true | Code examples are 50 % of correctness issues ([Aghajani 2019](https://emadpres.github.io/pdfs/icse2019.pdf)); incorrectness is a blocker ([Uddin 2015](https://www.cs.mcgill.ca/~martin/papers/ieeesw2015.pdf)) |
| Reading and extraction have no path | The home page's "What works today" table omits Extract; no extraction guide from code (one recipe); no guide for `@laminapdf/viewer` or the render packages; reveal and redaction only on CLI pages | Incompleteness is a blocker; HN's top complaint (431 comments, 116 threads) |
| One first-run path | Only a Node tutorial; Rust readers get an 18-line quick start; no CLI tutorial | Both reading styles start from example code ([Meng 2019](https://mangold-international.com/resources/meng-et-al-how-developers-use-api-documentation-2019.pdf)); "a zeroth step missing" ([HN](https://news.ycombinator.com/item?id=50042407)) |
| Results behind a tab | The Result tab is never remembered, and Edit and run sits inside it; 6 of about 22 TS examples run, none in "Your first PDF" | Showing the result early is a house SHOULD; readers start from examples |
| Top-level type split | "Recipes" (16 pages) and "Concepts" sit beside task groups; two recipes are missing from the sidebar, breaking the house MUST | Type-based top levels confused readers ([Meng 2019](https://mangold-international.com/resources/meng-et-al-how-developers-use-api-documentation-2019.pdf)) |
| Thin troubleshooting | One page, 10 entries, all JavaScript setup; nothing for Rust, the CLI, extraction quality or rendering | Robillard & DeLine's "matching APIs with scenarios" |
| Inline styles | `style-src 'unsafe-inline'` because Expressive Code colours tokens with style attributes | ADR 0011's strict headers; the website already avoids it |
| No reader data | ADR 0011 allows only opt-in telemetry; no analytics, no search logs | Self-reports overstate docs use: engineers claimed about 40 % of their time on docs but 3 % of logged events were docs ([Lethbridge et al. 2003, second-hand via Meng](https://mangold-international.com/resources/meng-et-al-how-developers-use-api-documentation-2019.pdf)) |

The site's weight is not a problem. A typical page is about 60–75 KB gzip before images; about 27 KB gzip of that is the search UI on every page, in line with stock Starlight, and the 166 KB gzip editor loads only when a reader presses "Edit and run" ([current_docs_site.md](developer-docs/current_docs_site.md)).

## Starlight stays: every alternative costs more and fixes nothing that matters here

Moving off Starlight would not address any gap in the table above, and most alternatives would break ADR 0011 or add weight. Starlight is healthy: release 0.42.10 came out on 6 November 2026 (main pins 0.42.8), it draws about **2.18 million npm downloads a week**, more than Docusaurus (1.96 M) or VitePress (1.98 M), and its maintainers now work at Cloudflare, which announced on 16 January 2026 that the Astro team was joining it while Astro stays MIT-licensed and platform-neutral ([npm](https://registry.npmjs.org/@astrojs/starlight), [npm downloads](https://api.npmjs.org/downloads/point/last-week/@astrojs/starlight), [Cloudflare](https://www.cloudflare.com/press/press-releases/2026/cloudflare-acquires-astro-to-accelerate-the-future-of-high-performance-web-development/)). The real cost is churn: Starlight is still 0.x, shipped 12 minor releases from 0.31 to 0.42 in about 22 months, and Astro had two majors in 2026, so each of the site's overridden components is upgrade work ([npm](https://registry.npmjs.org/@astrojs/starlight), [npm](https://registry.npmjs.org/astro)).

The research measured script weight on each framework's own docs site on 2026-11-11 (its own measurement, not a published benchmark): **Starlight about 6 KB gzip**, VitePress about 85 KB, Mintlify about 385 KB, Docusaurus about 489 KB, Fumadocs about 514 KB, Nextra about 710 KB and Rspress about 1.5 MB ([docs_frameworks.md](developer-docs/docs_frameworks.md)). Hosted platforms fail ADR 0011's "no third-party origins" outright: Mintlify Pro costs $450 a month billed annually and self-hosting is Enterprise-only, and GitBook's custom domains start at $65 a month per site — for Markdown twins and llms.txt that Lamina PDF already builds ([Mintlify](https://www.mintlify.com/pricing), [GitBook](https://www.gitbook.com/pricing)). Nextra has not released since December 2025, Material for MkDocs' maintenance window closed on 5 November 2026, and VitePress 2 has been in alpha all year ([npm](https://registry.npmjs.org/nextra), [mkdocs-material #8523](https://github.com/squidfunk/mkdocs-material/issues/8523), [npm](https://registry.npmjs.org/vitepress)). Switching also would not fix the CSP gap, because Shiki-based highlighters emit style attributes in every framework ([astro-shield issue](https://polar.sh/kindspells/astro-shield/issues/140)); the fix is class-based token colours, which `apps/site` already uses. A custom Astro site without Starlight would weigh the same but means rebuilding the sidebar, table of contents, search modal, theme switch, mobile menu and accessibility work, and replacing `starlight-typedoc` and the link validator; no published effort figure exists, and the layouts the redesign needs fit Starlight's overrides, route data and `StarlightPage`. The live-example route also works on Starlight: a component rendered with `client:visible` that loads `@laminapdf/sdk` from the site's own origin, which the existing runner already does. Sandpack and StackBlitz embeds load from their own origins and break ADR 0011 on any framework, and WebContainers need the cross-origin isolation ADR 0009 rules out ([web.dev](https://web.dev/articles/why-coop-coep), [WebContainers](https://webcontainers.io/guides/browser-support)).

On the flow of the docs, the evidence supports keeping the story for first-time readers and changing the top level for returning ones. The opening sequence (what it is, install, your first PDF) answers the HN complaints about READMEs that never say what the software does. Below it, Meng's finding argues for task areas in which recipes, guides and troubleshooting entries sit together, rather than a separate "Recipes" group of 16 pages. This is a modest change, not a rewrite, and the evidence for it is one study of 11 people, so it should be tested with readers before and after.

On agents, keep what exists and do not add a chatbot. Ahrefs' study of 137,210 domains found that **97 % of the roughly 38,000 valid llms.txt files received no requests in May 2026**, and that among named tools GPTBot fetched most and **Claude Code second** ([Ahrefs](https://ahrefs.com/blog/llmstxt-study/)): llms.txt costs nothing to keep, and the readers who do fetch it are coding agents, which are Lamina PDF's audience. The Markdown twins and the docs shipped in packages matter more than the index file. AI chat widgets are vendor products whose value claims are deflection figures (Kapa reports 20–70 % fewer support cases at named customers, none audited) for a support desk the project does not have ([Kapa](https://www.kapa.ai/library/how-ai-platforms-reduce-support-costs-and-how-to-compare-them-(2026))), and HN regards hallucinating doc bots as worse than none.

## Recommendations, in order

The order below weighs how strong the evidence is against how much work each change takes. "Opinion" marks a recommendation that rests on my judgement or on vendor claims rather than on measured findings.

| # | Change | Evidence behind it | Strength |
| --- | --- | --- | --- |
| 1 | Generate every CLI transcript and `sh` block from a real run in the build, and fail on drift, so the home page's "every code block is tested" promise holds everywhere | Examples are 50 % of correctness issues; incorrect docs are blockers; HN's tested-examples consensus | Strong (studies + 481 HN comments at ~6/8) |
| 2 | Add a reading path: "Extract" on the home page's table, an extraction guide in TypeScript and Rust, and guides for the viewer and render packages and for reveal and redaction from code | Incompleteness is a blocker; missing docs is HN's largest complaint (431 comments, 116 threads, ~7/8) | Strong |
| 3 | Show the first page picture beside the code by default (static, no script), and keep Edit and run one click from it rather than inside a tab; make "Your first PDF" runnable in the browser | Readers of both styles start from examples ([Meng](https://mangold-international.com/resources/meng-et-al-how-developers-use-api-documentation-2019.pdf)); the house rule "show the result early" | Moderate; the side-by-side gap among PDF libraries is my inference |
| 4 | Add first-run tutorials for Rust and the CLI, each checked as an example, with the version pin explained in the first step | One Node-only path today; "a zeroth step missing" ([HN](https://news.ycombinator.com/item?id=50042407)) | Moderate |
| 5 | Fix the two recipes missing from the sidebar now; then fold recipes and troubleshooting entries into task areas (create, read and extract, edit and save, render and view, command line), keeping page types as labels inside each; do W3h's question-style titles in the same change | Type-based top levels confused readers (n = 11, [Meng](https://mangold-international.com/resources/meng-et-al-how-developers-use-api-documentation-2019.pdf)); house MUST | Moderate, test with readers |
| 6 | Grow troubleshooting by area (Rust, CLI, extraction quality, rendering), symptom first, and link each error-code page from the error's `docsUrl` prominently in CLI output | Scenario matching ([Robillard & DeLine](https://www.cs.mcgill.ca/~martin/papers/ese2011.pdf)); HN delight at errors that link to docs (few comments) | Moderate for troubleshooting, weak for the error-link counts |
| 7 | Colour code tokens with classes, as `apps/site` does, and drop `style-src 'unsafe-inline'` | ADR 0011's strict headers; the cause is the highlighter, not Starlight | Strong (a constraint, not a reader finding) |
| 8 | Stay on Starlight; pin minors, keep overrides few, and upgrade one minor per small PR | 6 KB vs 385–710 KB of script; hosted options break ADR 0011; switching fixes no gap | Strong on cost, opinion on the upgrade policy |
| 9 | Offer each area as one long page and the whole guide as a PDF built by Lamina PDF itself | Offline/single-page: 252 HN comments at ~7/8; Lua and Node praised for one page | Moderate; the self-built PDF is opinion, though a fitting demonstration |
| 10 | Add a `rel="alternate" type="text/markdown"` link per page and a "copy page as Markdown" button; keep llms.txt; add no chatbot | Claude Code is a leading llms.txt reader ([Ahrefs](https://ahrefs.com/blog/llmstxt-study/)); HN distrust of doc bots (100 comments at ~6/8); SO's 66 % "almost right" | Moderate; the alternate link is from the llms.txt proposal, adoption unmeasured |
| 11 | Mark when each API item was added or changed, and keep each released version's docs at a stable URL once 1.0 ships | Django and PostgreSQL praise; versioning counts were unusable, so quotes only | Weak, opinion |
| 12 | Split API pages into reference and usage with troubleshooting, react.dev-style, starting with `Document` and `Builder` | [react.dev](https://react.dev/blog/2023/03/16/introducing-react-dev); "examples plus reference" on HN | Opinion |
| 13 | Measure without telemetry: run the L5b agent eval, and pay a few developers to follow the quick starts and the reading path, recording where they stop | No analytics under ADR 0011; self-reports overstate docs use (second-hand figure); the README-following HN thread | Moderate |

Two things to leave out for now: Twoslash hover types, which would add script and probably inline styles to every code block, and personalised or account-aware samples in Stripe's style, which have nothing to personalise in a library with no accounts.

## Conclusion

The evidence moves the redesign's centre of gravity away from the site's look and framework and towards its guarantees. Lamina PDF's strongest asset is a promise most docs sites cannot make — that the code shown is the code that ran and produced the page in the picture — and the most valuable work is to make that promise complete (the CLI and shell blocks) and visible (results beside code, not behind a tab), then extend the content to the reading half of the library, which today has almost no path. In a period when readers check "almost right" AI answers against the source, and coding agents fetch Markdown pages directly, a verifiable statement is worth more than a polished one.

The second change in understanding is about what is not known. Almost every number on interactivity, AI assistants and llms.txt comes from vendors or from keyword counts with modest precision, and the one study of how people read API docs watched eleven of them. Because ADR 0011 rules out the usual analytics, the project should treat its redesign as an experiment it measures by other means — the agent eval and observed first runs — and change the top-level structure only once those show readers getting lost where the evidence predicts.
