## Goal

Bring the whole flow layer to `@laminapdf/sdk` as typed objects: `builder.flow(document, { data })` takes a `laminapdf.document/1` document, checked by `tsc` against types generated from [T4e](../done/T4e-json-documents-and-templates.md)'s committed schema, and fills it from data in every runtime. L3e brought extraction to TypeScript this way after L3a–L3d built it in Rust. Filling a template from data is the second-largest generation request on Hacker News, about 560 comments, and one commenter put the use case in one line: "It’s absolutely trivial for example to build a Lambda function that parses some json input into a PDF." ([45394409](https://news.ycombinator.com/item?id=45394409)). A typed document lets an editor catch a misspelt key before anything is drawn.

- [T4e](../done/T4e-json-documents-and-templates.md): `crates/laminapdf-build/schemas/document.schema.json`, `laminapdf::flow::document::fill`, the `invalid-document`, `template-data-missing` and `template-data-type` errors, and `invoice_from_json.rs` with its golden. See [L3e](../done/L3e-extract-bindings-and-benchmark.md).
- Unknown keys in a binding record: `unknown-option` ([ADR 0016 §7](../../decisions/0016-package-design.md#7-api-naming-and-shape-at-the-wasm-boundary)) with a `didYouMean`.
- The runtime suite's `measure()` (`packages/sdk/test/suite/examples.ts`) records timings per runtime. [T1c](../done/T1c-publish-performance-numbers.md) adds a one-page `invoice` case there, publishes generation timings, and leaves flowing-layout timings and a two-page invoice to this round. ## Scope

**In scope**

- **WebAssembly:** `WasmBuilder.flow(document, data)` in the text module, with fonts and images by name, and `laminapdf-build`'s `serde` feature turned on in that build. `cargo xtask size` passes within ADR 0032 §9's 1,280,000 B.
- **TypeScript:** `builder.flow(document, { data })` in `@laminapdf/sdk`, with fonts and images as `Font` and `Image` handles by name. The `FlowDocument` types are generated by `cargo xtask gen boundary` into `packages/sdk/src/generated/document.ts` from the committed schema, extending `schema_ts.rs` for any keyword the schema adds.
- **The TypeScript example:** `packages/sdk/examples/invoice-from-json.ts`, paired with T4e's `invoice_from_json.rs` in `tools/xtask/docs-snippets.toml`, writes the same golden bytes and joins the runtime suite.
- **Timing:** the two-page invoice joins `measure()` as its own case, `invoice-from-json` (beside T1c's one-page `invoice`), so `cargo xtask pdf-runtimes` records it in each runtime as `pdf/<runtime>/invoice-from-json`, for T1c's page to show.

**Out of scope** (and which todo covers it)

- The format, validation, templates, the CLI and MCP inputs: [T4e](../done/T4e-json-documents-and-templates.md).
- A `FlowJob` stepped by page: only if T4b's benchmark exceeds ADR 0032 §9's budget in WebAssembly, in its own todo.
- A JSX layer over the typed objects (ADR 0032 §6 leaves it for later), and a visual template designer.
- Publishing the timings: [T1c](../done/T1c-publish-performance-numbers.md).

## Risks and open questions

- **The schema converter.** `schema_ts.rs` knows only the keywords the extract schema uses, and fails on any other. It handles `oneOf` and `const`, which tagged unions need; check what schemars writes for the flow model before relying on that.
- **WASM size.** The text module's budget covers the flow layer, tables, notes, Markdown and templates together. If T4i left too little room, measure what `serde` adds and report it to the owner before raising anything.
- **Speed in WebAssembly.** The spike's 100-page report took about 280 ms per pass in Node 24. If the recorded figures pass ADR 0032 §9's budgets, open the `FlowJob` todo rather than slowing this one.

## As built

- **Generated types.** `schema_ts.rs` gained `additionalProperties`: a map with a value schema is a `Record<string, …>`, `false` beside properties needs nothing (TypeScript already refuses an unknown key in an object literal), and properties beside a value schema fail. `cargo xtask gen boundary` writes `packages/sdk/src/generated/document.ts` with the root type `FlowDocument`.
- **Templates in TypeScript.** The generated types describe a plain document, so a template needs its own type: `Templated<T>` allows `$data`/`$item` where a value goes and `$each`/`$if` among a list's items, and `FlowTemplate` is `Templated<FlowDocument>`. `builder.flow` takes a `FlowTemplate`; a `FlowDocument` is one too.
- **WebAssembly.** `WasmBuilder.flow(document, resources, options)` in the text module (`src/builder/flow.rs`), with `WasmFlowResources` holding the fonts and images by name (a record can't hold WebAssembly objects). The document and data cross as JSON, so integers stay integers. The text module's `text` feature turns on `laminapdf/document`.
- **Profiles.** As in Rust, the document's `profiles` don't reach the builder by themselves: the builder's options take them. A template's `profiles` may be a placeholder, so the TypeScript example names `PDF/UA-1` itself rather than reading it from the template.
- **Size.** `WasmBuilder.flow` links the document format into the text module: reading, checking, filling and converting it, about 75 KB gzip in all (1,391,637 B), spread over many small functions (the largest, `convert_block`, is 7 KB). That passed the 1,360,000 B budget by 31.6 KB, and the owner raised it to 1,400,000 B (ADR 0016 §6 and ADR 0032 §9 amended).
- **Timing.** `measure()` records `invoice-from-json` as the best of 30 runs (ADR 0032 §9's figure), beside the medians of the other cases.
- **The guide.** "Pages that flow" gains a TypeScript paragraph in its JSON section and drops "the TypeScript package will follow". Its other sections show the Rust flow API, whose elements TypeScript reaches through the JSON document, so they keep their Rust examples.
