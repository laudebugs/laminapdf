## 1. Goal

The docs site exists and its examples are tested. But it reads like a repository tour, not a guide. Three of the six runtime pages show CI test runners where readers expect an app, every example carries scaffolding from the reference-PDF tests, and the sidebar follows the folder layout.

The code is held to strict lints, but nothing yet guards file size, duplication across crates and packages, or the readability of what we show readers.

Round Q fixes what exists and adds the rules and checks that keep it fixed:

- **The docs read as one story.** A reader goes from "what is lamina" to a PDF on disk in five minutes, then through the ideas, the everyday tasks, production concerns and the reference, in that order.
- **Every page is plain English.** Jargon is explained where it first appears, or linked to a glossary. Reader-facing text never mentions ADR numbers, todo IDs or CI.
- **Examples are code you would merge.**
  - They read top to bottom, use only the public API, free what they create and name their numbers.
  - They carry no test scaffolding.
  - The TypeScript and Rust versions of a task match.
- **Code stays maintainable.**
  - A guideline says what "maintainable" means here: size budgets, one home per concept, reuse before re-implementing.
  - CI checks what can be checked.
- **The standards bind future work.** The guidelines, CLAUDE.md and the `/code-review` standards axis all point at the new rules, so every later PR is reviewed against them.

## 2. What the review found (2026-10-31)

Six read-only reviews covered the docs prose and navigation, the code examples, the TypeScript packages and the Rust crates (in three groups). The findings below are summaries; each todo links the files and lines.

### 2.1 Docs prose and navigation

- **Wrong code on the runtime pages.** Three of the six runtime pages show CI test runners instead of an app:
  - Deno and Bun show `packages/sdk/test/{deno,bun}/examples.test.ts`.
  - Node shows `test/examples.test.ts`.
  - The browser page shows a Vite test app that returns page counts and builds nothing a reader can see.
- **No first-PDF path and no concepts page.**
  - The overview asks the reader to choose among six runtimes before they've learned anything.
  - The key ideas appear only as asides on runtime pages:
    - bytes in, bytes out, and the same input always giving the same bytes;
    - your edits kept apart from the opened bytes, then saved incrementally or as a full rewrite;
    - the base, text and extract modules, and freeing WebAssembly memory;
    - page coordinates.
- **Spec jargon with no "why".**
  - Guides open on an API call.
  - They use spec terms the reader hasn't met: Type 0, `/W`, ToUnicode, export condition, glue, overlay, DocMDP, `/Kids`, golden.
  - Sentences are short; the problem is density, not length.
- **Internal IDs on reader pages.**
  - 45 of the 117 error-code pages (`docs/errors/*.md`, rendered at `/reference/codes/*`) put ADR numbers or todo IDs in reader text.
  - The SDK README, rendered by TypeDoc, does the same.
  - The Rust reference page talks about "the fast lane".
- **Inconsistent terms.**
  - "Worker" means both a Cloudflare Worker and a Web Worker.
  - "golden" is never defined.
  - "standard 14" is spelled three ways.
- **The sidebar follows the folders.** It is autogenerated from `sidebar.order`, so Errors and warnings comes sixth among the guides, though readers need it early.
- **The repository README is stale.** It never links docs.laminapdf.com and still says the site lives on workers.dev.
- **One factual error.**
  - `encrypted-files.mdx` says the password is tried as the user password, then the owner password.
  - For R5/R6 the order is owner first (`laminapdf-syntax/src/crypt`).

### 2.2 Code examples

The plumbing is sound:

- every snippet is a real file run in CI, in Node, three browsers, Deno, Bun and workerd for TypeScript;
- the TypeScript and Rust outputs are byte-identical to the reference PDFs;
- every shown file has a header comment, though only by convention.

What readers see is not:

- **Test scaffolding in every example.**
  - The fixed file ID `lamina-ex-…`, the fixed creation date and the fixed producer appear 13 times (7 TS, 6 Rust). A reader who copies `hello` ships every PDF with the same file ID.
  - Some examples check their own output and throw (`generate-then-edit`).
  - Some exist with a seam only for tests: `invoice::builder` is `pub(crate)` so tests can read diagnostics.
- **Leaked WebAssembly memory in TypeScript.**
  - Five examples end in `return b.finish().save()` and never free the document.
  - Three others free it with 6–10 lines of `try`/`finally`.
  - `Document` and `Builder` already implement `Symbol.dispose`, so `using` fixes both.
- **API friction that shows up as noise.**
  - `TextRun` is `#[must_use]` although the text is drawn either way, which forces 12 `let _ = s.text(…)?` lines in the Rust examples.
  - There is no `RectPt::from_points`, so three examples write their own `rect()` helper.
  - `Document.save()` returns a bare `Uint8Array`, so the Worker example casts.
- **Unnamed numbers and long functions.**
  - `invoice` hard-codes the A4 width (595.28) and row arithmetic.
  - `report` hides its fake data in `(n*37+row*11)%500`.
  - `invoice.rs` is one 97-line function.
  - `images-and-vectors` is a feature tour rather than code to maintain.
- **Internal references in headers readers see:** todo IDs, ADR numbers, "the TS twin of…", "the Rust golden".
- **Examples that only work inside this repository.**
  - The Worker example imports `../../../../../fixtures/fonts/…`.
  - `worker-client` returns a shape built for its test (`progressEvents`, `abortedAsCancelled`) instead of taking `onProgress` and `signal`.
- **The TypeScript and Rust versions drift apart.** Names don't match (`images-and-vectors.ts` vs `vectors.rs`), and neither do helper styles or header wording.

### 2.3 Code quality and reuse

The code is disciplined where rules already exist. Workspace clippy `pedantic` runs with `-D warnings`, so `too_many_lines` (100) passes everywhere: only three functions opt out with `#[expect]`. Visibility is mostly `pub(crate)`. There is one error type per crate. The TypeScript is strict and well commented. The debt is where no rule reaches:

**Parallel implementations that already disagree.** These are bugs, not just tidiness:

- **Render ranges lost in the worker.** The worker turns a render error's `ranges` into `{offset, length}` objects (`packages/sdk/src/worker/server.ts`). `LaminaPdfError` only accepts `[offset, length]` tuples, so a render `data-pending` that crosses the worker arrives with no ranges.
- **I/O errors swallowed by text extraction.** Extraction has its own error-propagation rule (`laminapdf-text/src/extract/font.rs` `fatal`) that leaves out `Error::Source`. An I/O failure from a `FileSource` reads as "no font", against ADR 0003.
- **Surrogate pairs split.** There are two ToUnicode CMap writers in laminapdf-text, and the simple-font one can split a surrogate pair that the Type 0 one never splits.
- **"Did you mean" that depends on the layer.** It is written in both Rust (`laminapdf-wasm`) and TypeScript (`@laminapdf/sdk`), and they break ties differently, so a typo's suggestion depends on which layer raised it.
- **`/Rotate 90.0` read as unrotated.** `/Rotate` and `/MediaBox` are parsed in both `laminapdf-cos` and `laminapdf-model`, and ops (`rotate.rs`) reads the cos copy, which accepts integers only.
- **Two `Matrix` types that compose in opposite orders.** laminapdf-build composes with `after` and laminapdf-content with `multiply`, so a matrix moved from one crate to the other needs its order reversed. `FillRule`, `Dash` and `Color` are also defined in both crates.

**Second implementations of things the codebase already has:**

- **A second PDF serialiser.** The spike-era `Writer` in `laminapdf-save/src/legacy.rs` carries its own xref, object-stream and header code, and it sits in laminapdf-save's public API although only tests use it.
- **A second PDF lexer** in `laminapdf-text/src/extract/cmap.rs`, about 150 lines, that skips `#xx` name decoding and ignores `Limits`.
- **Two sets of PNG row filters**, in laminapdf-build and laminapdf-syntax.
- **Two copies of the ADR 0026 error object**: the façade's `Diagnostic` and laminapdf-wasm's `BindingDiagnostic`.
- **Two error serialisations for render errors.** One of them is unused; the viewer throws plain objects.
- **A duplicated rotation enum.** `ViewRotation` copies `Rotation`.
- **Hand-kept lists across the WASM boundary.**
  - Fill rules, caps, joins, blend modes, artifact kinds and scopes are kept by index on both sides, with no check.
  - The render error codes and `HAYRO_VERSION` are hand-copied into TypeScript.

**Test helpers copied everywhere.**

- **Rust:**
  - `fixtures_dir` has 11 copies, `fixture` about 9, `corpus` 4, the classic-xref file builder 5, and the `ByteSource` fakes about 15.
  - 35 `#[path = "../../other-crate/…"]` includes link crates' tests together, invisibly to cargo.
- **TypeScript:**
  - The render adapters import `../render/test/…` by relative path, which code-organization §2 forbids.
  - The Firefox profile workaround is copied three times.

**Test hooks in shipped code.**

- `renderLog` in the viewer's worker grows on every render and is never trimmed.
- `__busy`, `__crash`, `__budget` and `__stats` are part of the public method types.

**Large modules.**

- `laminapdf-cos/src/reader/mod.rs` is 1,533 lines (1,080 of them code).
- `laminapdf-content`'s `execute` is 318 lines behind an `#[expect]`.
- Four other files are over the 800-line budget in total lines: `laminapdf-text/src/extract/font.rs` (1,321), `laminapdf-build/src/surface/mod.rs` (1,027), `laminapdf-wasm/src/builder.rs` (1,011) and `laminapdf-build/src/surface/png.rs` (872). In non-test lines, all four are within the budget (`laminapdf-text`'s `font.rs` is the closest, at 786). Q2a's baseline (`tools/xtask/maintainability-baseline.toml`) lists the four modules that are over it. They are the COS reader (1,080), `laminapdf-content`'s `interp.rs` (824) and two xtask modules (`live.rs`, 1,115; `render_diff.rs`, 923). Q2r now splits the two xtask modules too; [Q2q](../todos/done/Q2q-split-cos-reader.md) and [Q2w](../todos/done/Q2w-split-content-interpreter.md) have taken the COS reader and `interp.rs` off the baseline.
- In TypeScript, eight functions are over Biome's cognitive-complexity limit of 15; the PDFium `render` closure scores 39.

**Façade names that collide.** Readers of the docs meet:

- `laminapdf::TextRun` (drawn text) next to `laminapdf::extract::TextRun` (extracted text);
- `Font` next to `FontHandle`;
- `ops()`, which hands out a second `Document` type.

The façade also re-exports every wrapped crate's error type, against rust.md's "SHOULD NOT expose another crate's error type".

**History in names.**

- Test files are named after reviews and todos (`review_b4b.rs`, `review_fixes.rs`, `b5b.rs`).
- 77 todo IDs sit in `src/` comments, where they explain nothing.

## 3. The docs as a story

The sidebar becomes an explicit list in `apps/docs/astro.config.mjs`; `autogenerate` is dropped, so the order is a decision, not a side effect of file names.

```
Start here
  What is lamina            what it is, who it's for, what works today
  Install
  Your first PDF            Node, five minutes, writes hello.pdf and opens it
Your runtime                one runnable app each, plus what is different there
  Browser and bundlers · Node · Deno · Bun · Cloudflare Workers · Rust
Concepts
  How lamina thinks about a PDF   bytes in and out; the opened bytes and your edits;
                                  incremental save vs full rewrite; the base, text and extract
                                  modules; same input, same bytes; freeing memory
  Pages and coordinates           points, top-left origin, y down, 0-based page index
  Errors and warnings
Create PDFs
  Text and fonts · Shapes, colour and images · Links, outlines and metadata · Accessible PDFs · Archival PDFs
Read and edit PDFs
  Edit a PDF                (transactions, undo)
  Save a PDF                (modes, signatures)
  Open password-protected files
  Open files you don't trust
Production
  Keep the page responsive  (Web Workers)
Recipes                     one page per example; the Cloudflare Worker gets a real page
Troubleshooting             symptom → cause → fix
Reference
  @laminapdf/sdk · Rust API · Error and warning codes · Glossary
```

Every guide and recipe opens with what you'll make and when you'd need it, then the code, then the details. Spec terms move into a "Details" aside, or link to the glossary on first use.

## 4. Standards

Three new guidelines hold the rules; this plan doesn't restate them, so there is one copy to keep current. CLAUDE.md names all three, so every session applies them, and every `/code-review` applies them too, because its standards axis reads the guidelines.

| Guideline | What it asks | How it's checked |
| --- | --- | --- |
| [Writing docs](../guidelines/docs-writing.md) | Pages in story order; a first paragraph that says what you'll make; plain English with no internal IDs; one term per thing; a pleasure to read | `cargo xtask check docs-prose` in `check docs` (Q1b); reviewers and `/writing-review` for the rest |
| [Code examples](../guidelines/examples.md) | Examples from `examples/` only; public API only; no test scaffolding; `using`; named numbers; small functions; matching TS and Rust pairs | `cargo xtask check docs-snippets` in `check docs`, a Biome override in `check ts`, `cargo xtask clippy-examples` in `check rust` (Q1c) |
| [Maintainable code](../guidelines/maintainability.md) | One home per concept; size budgets whose baseline only shrinks; one public path per item; no test code in shipped code; one error serialiser per language | `cargo xtask check maintainability` (Q2a, extended by Q2c, Q2e, Q2i, Q2t); Biome and TypeDoc rules (Q2b); dependency-cruiser, jscpd and knip (Q2u) |

**The checks bind while we write.** From the day each check lands, it is strict on every file a PR adds or changes, and it only warns on files nobody has touched yet. So a new page or example is checked as it is written, and the rewrite todos clear the rest; Q1l then makes the docs checks strict everywhere, and each maintainability check becomes strict as its baseline reaches zero. The docs checks need no build and run in about a second, so authors run them while drafting.

**No new dependency for the docs checks.** Vale (MIT) would need a Go binary and an extra MDX tool in CI for a subset of the rules, so the docs checks are written in xtask. The TypeScript maintainability tools (dependency-cruiser MIT, jscpd MIT, knip ISC) pass the licence policy (ADR 0019) before they land.

## 5. The font

The docs site uses **Source Sans 3** for everything; code stays on the system monospace stack.

**Why Source Sans 3:**

- It is already self-hosted and licensed under OFL-1.1.
- It is a variable font with italics, Latin Extended and tabular figures.
- It is the app's own UI face.

Inter and IBM Plex Sans (both OFL) were considered. They are not clearly better, and either would add files and licence entries.

**What changes:**

- The four Newsreader files (about 461 KB) leave `apps/docs`.
- Headings carry the hierarchy with weight (600–700) instead of a second family.
- The design language records the docs site as sans-only: §3's "Site display" row and §7.39's wordmark.

The product app keeps Newsreader for titles unless the owner decides otherwise (§8).

## 7. Risks

- **The prose lint could become a box-ticking exercise.** Its rules are deliberately few and mechanical; judgement stays with the `/code-review` standards axis and the guideline's checklist. A rule that keeps producing false positives is removed, not worked around.
- **Example refactors could change the reference PDFs.** CI byte-compares them, so any change to the output shows up. The example todos say whether their reference PDFs may change; pure refactors keep them byte-identical.
- **Two sessions could edit the same sidebar or guideline.** The Q1 todos chain through `Depends on`, so they don't compete for `astro.config.mjs` or the same pages.
