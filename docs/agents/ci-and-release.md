# CI lanes and releases

How the PR lanes, the nightly lane and the release lanes (library, CLI, desktop, web reader) run, and what each checks.

## CI lanes


CI has two required PR lanes ([ADR 0018 §2](../decisions/0018-test-strategy.md#2-ci-lanes)). Native Rust checks run on standard GitHub-hosted Linux, macOS and Windows, each on x64 and Arm64; macOS x64 only on pushes to `main` and in the nightly (`rust-macos-x64`, X9a), since its runners queue longest. Every leg that runs blocks `fast-gate`. The full lane's `gate` requires the Linux Arm64 Rust/TypeScript check, the whole `cargo xtask check` on Windows x64 (`check-windows`, X6), and the differential, fuzz and PDF suites; and, on a PR that changes one, the sampled live differentials (`live-differentials`). Every other job runs on Ubuntu x64; macOS Arm64 only where a Mac is needed (WebKit, the render goldens, the CLI's macOS build). Docs-only PRs skip the suites, while `changes` still runs docs checks, and other PRs skip each group of jobs their paths can't affect (`render`, `rust`, `ts`; CI caching plan §8.1). The desktop build and e2e legs also skip on a PR when its own runs or `main` already passed them on the same inputs (`desktop-key`, X10b), CodeQL analyses only the languages a PR changes (X10c), and the runtime legs run only the browser suites the dependency graph says a PR's paths reach, the server leg only for the SDK's examples (`runtime-legs`, X12; CI caching plan §8.3). All runners are fresh VMs; Rust and pnpm caches save only on pushes to main (pull requests, schedules and dispatches only restore them), and jobs that build the same thing share one Rust cache (`shared-key` `rust`, `wasm` or `xtask`, saved by one job; the nightly and release lanes save none). There is no compile cache: X8a's trial of sccache over Cloudflare R2 saved too little, so X8b removed it (2026-11-15; [CI caching plan §2.2](../plans/ci-caching.md#22-the-trials-results-x8b)). No active workflow uses a self-hosted runner or its heartbeat. See [hosted runners and the public transition](../public-readiness.md).


Every Linux apt install goes through `.github/actions/apt-install`, which takes the packages and a per-try `timeout` (900 s by default, at most 1,100 s); its callers are `linux-webkit`, `playwright-deps`, `poppler`, `differential-tools`, `desktop-build` and the nightly's `signed-saves`. It runs `apt-fail-fast` first: each download gets 30 s and 3 tries, and on x64 runners Kernel.org's CDN-backed mirror goes last in Ubuntu 24.04 (noble)'s `/etc/apt/apt-mirrors.txt`. Then it makes up to three tries a minute apart under `nick-fields/retry`. Each try runs `dpkg --configure -a` (to finish what a cut-off try left), `apt-fail-fast/update.sh` and the install, every root process under `sudo timeout`. The .deb files are cached with `actions/cache`, keyed on the runner image (`ImageOS`, `ImageVersion`), the arch and the package list; every run restores them, and only pushes and scheduled runs on `main` save. `playwright-deps` takes its list from `playwright install-deps --dry-run` and installs it through the same action ([`ci-apt-slow-or-unreachable-mirror`](../bugs/ci-apt-slow-or-unreachable-mirror/resolution.md)).

## Fuzzing


Fuzzing (`fuzz/`, see its README) needs nightly Rust and cargo-fuzz (pinned in `doctor.rs`). Python (pypdf, pinned in `tools/corpus-facts/requirements.txt`) is only needed to regenerate facts; tests read the committed JSON.


## The nightly lane


The nightly lane (`.github/workflows/nightly.yml`, cron, `workflow_dispatch`, and `workflow_call` for the release lane; ADR 0018 §2) runs on `main`, on GitHub-hosted Ubuntu x64 runners with explicit tool setup (`pdf-runtimes`' WebKit leg and `render-diff`, whose thresholds were measured on macOS, on macOS Arm64): the live differential, every fuzz target of `harness::FUZZ_TARGETS` for 10 minutes (corpus kept in the Actions cache; each run uploads its `target/xtask/fuzz/<target>.json` summary), the scaling tests, the round-trip suite (`roundtrip`: `cargo xtask roundtrip`, set up as the full lane's `suites` job, in `bench`'s `needs`), the annotation appearance parity suite (`annots-parity`, on macOS Arm64 where its goldens are made: `cargo xtask annots-parity --corpus`, every annotation subtype by pdf.js, PDFium and hayro against the goldens and against PDFium, then the pdf.js corpus's annotations moved, saved and checked against the outcomes pinned per file; diff images in the `annots-parity-diff` artefact on failure), the benchmarks (after every job that doesn't depend on them, whatever its result; history in `history.jsonl` on the `bench-data` branch, under the runner label `github-hosted/ubuntu-24.04-x64`), `@laminapdf/sdk` in every runtime with its timings and WebAssembly memory appended to the same history (`pdf-runtimes`, after `bench`, over the WebAssembly the `wasm` job builds once on Linux for both legs; `pdf/<runtime>/<case>` keys; recorded, never a regression issue), the hayro-vs-PDFium render diff (`render-diff`, X3b: `cargo xtask render-diff --pages 20` over the external corpus with PDFium from `cargo xtask fetch-pdfium`; the pass+minor share per source appended to the same history as `render-diff/<source>` basis points, with the sampling; a drop of more than 2 points against the last point from the same runner and sampling opens "Nightly render-diff regression on <ref>", never a failure; report and diff images in the `render-diff` artefact; every job that fetches the history pushes it with `.github/actions/bench-history`, which retries a refused push), the proof record (`proof`, T1a: after `differential`, `fuzz`, `scaling`, `render-diff`, `verapdf`, `roundtrip` and `pdf-runtimes`, whatever their results, it downloads each one's report to the path its job wrote and runs `cargo xtask proof --jobs "$NEEDS"`; a full-budget night on `main` appends the `kind: "proof"` record to the same history, under `github-hosted/ubuntu-24.04-x64`; uploaded as the `proof` artefact), veraPDF (`verapdf`, B8b: `cargo xtask verapdf` over every example that claims a profile; any violation fails; writes nothing but its artefact) and the external link check (`links`: a URL whose page or site is missing (404, 410, another error status, or no answer) doesn't fail it: it gets a `::warning::`, `missing=true` and a row with its reason in `missing.md`, from which the report job opens or comments on "Missing links in the docs on <ref>"; a URL that passes only on a retry is reported as flaky; one whose last answer is 403 (not retried) or 429 (after its retries) is reported as refused, with a warning, and doesn't fail it; hosts that always refuse bots go in `.config/link-check.toml` with a reason). GitHub ends a timed-out job `cancelled`, usually because it landed on a hung runner, and the report counts it as a failure; a run someone cancelled opens no issue. A failed or timed-out job, a flaky scaling test or a flaky link opens or comments on the `nightly` issue "Nightly lane failing on <ref>", where flaky results, which passed on their retry, are marked as not blocking the release; a benchmark regression over 10% and a render-diff regression open their own issues and never fail the run; every write (history pushes, the fuzz cache, issues) is gated on the `record` input, which the release lane sets to `false` (`release_lane_should_call_the_nightly_lane_without_recording` in `tools/xtask/src/release.rs` checks each step). Its jobs are the `cargo xtask` tasks above. The live differential needs the corpus (`cargo xtask corpus fetch`), qpdf at the version pinned in `doctor.rs`, `pnpm --dir tools/differential install --frozen-lockfile` (pdf.js) and Python with `tools/differential/requirements.txt` (`$LAMINA_PDF_PYTHON`); every reader runs at once, in chunks of separate processes under time limits, so a crash or hang costs one file (`tools/xtask/src/runner.rs`). It fails when Lamina PDF disagrees with every tool on a fact and neither exceptions file (`fixtures/differential/exceptions.toml`, `full-exceptions.toml`) excuses it (per-file `[[exception]]`, value-matched `[[class]]` with its ADR 0003 rule, or `[[known]]` with its issue), when Lamina PDF panics, crashes or hangs on a file, or when a reader breaks or reports the wrong files. The same job then runs the text differential (`--live --text`, B9f): Lamina PDF's `text-facts` example (`crates/laminapdf/examples/differential/`) against `tools/differential/text.mjs --facts pdfjs|pdftotext` (pdftotext from the runner's poppler, only at the version pinned in `doctor.rs`: another version or none is a `::warning::` and pdf.js alone is compared, so pages where only pdftotext agrees fail; the nightly builds the pinned Poppler source with its SHA-256 checked) under the same runner, page by page with whitespace and bidi controls removed; a page fails when Lamina PDF matches neither tool that read it and no text `[[class]]` or `[[known]]` entry (`facts = ["text"]`, split off the facts lane's when the file is read) excuses it: classes match Lamina PDF's page text, its `page_error`, its warnings (`lamina_warning`) and the relation `unmapped`; a text `[[known]]` lists its pages per file in `[known.pages]`; entries that could have applied and excused nothing are reported as stale. Last comes the XMP differential (`--live --xmp`, E1c): Lamina PDF's `xmp-facts` example (`crates/laminapdf-model/examples/`) under the same runner against one `exiftool -j -G1 -n -XMP:all` run (ExifTool from Ubuntu's `libimage-exiftool-perl`, at the version pinned in `doctor.rs`) over the external corpus and the committed PDFs of `fixtures/corpus/`, `fixtures/golden/` and `fixtures/golden/examples/`, comparing `xmp::Packet`'s getters field by field; a field that differs fails unless a `[[known]]` entry of `fixtures/differential/xmp-exceptions.toml` excuses it. External corpus files are never committed.


## The library release lane


The release lane (`.github/workflows/release.yml`, ADR 0017 §6, ADR 0018 §2) runs on `v*` tags and on `workflow_dispatch` (`gh workflow run release.yml --ref <ref> [-f ref=<tag-or-sha>]`; a dispatched `ref` must be an existing `v<version>` tag or a full commit SHA on `main`, checked before any checkout, since every job runs that ref's code on main's caches): `guard` (`cargo xtask release-guard`: refuses unless the latest full nightly run on `main` succeeded on the release commit or an ancestor: a scheduled run, or a dispatch with every input at its default, which nightly.yml's `run-name` titles "Nightly (full budgets)"; other dispatches don't count (ADR 0018 §2); `version check-tag`), then the fast lane (`check`, `wasm` with publint/attw, `size`), the full lane's suites, `@laminapdf/sdk` in every runtime, the nightly lane (`nightly.yml` via `workflow_call` with `record: false`: nothing recorded, no issue; skipped when the guard's `--version-only` finds the release commit is only a version bump on top of the commit that nightly tested) and `cargo xtask verify-install` (Node 22/24/26, Deno, Bun, Chromium, workerd, Rust path + git dependency pinned to the tag); then, once the `release` job reports every check passed, the publish jobs (ADR 0017 §7): `publish-crates` (`cargo xtask publish crates`: `cargo publish --workspace` of the thirteen `publish = true` crates with a token from crates.io trusted publishing; with `publish-npm`, one of the two jobs with `id-token: write`), `pack-npm` (`cargo xtask publish npm-pack`: the fixed group built and packed with `pnpm pack`, plus `publish.json` with the version, dist-tag and tarballs in dependency order, uploaded as an artifact), `publish-npm` (on `ubuntu-latest`, since npm's trusted publishing accepts only cloud-hosted runners, with no checkout: each value in `publish.json` checked, then `npm publish --ignore-scripts` of each tarball in its order with npm 11.17.0, pinned in its own install step, which trades the job's OIDC token for a short-lived publish token; no stored npm token, no approval step, packages already at the version left out) and `github-release` (`cargo xtask sbom`: CycloneDX SBOMs, attached to the GitHub release with `cargo xtask release-notes`' CHANGELOG section). Only a tag push publishes (`github.event_name == 'push' && github.ref_type == 'tag'`); a dispatch, even on a tag, runs every step with `--dry-run`, and a re-run skips what is already at the version (`release_workflow_should_publish_only_from_its_publish_jobs_and_only_on_a_tag_push` in `tools/xtask/src/release.rs` checks it).


## The CLI, desktop and daily releases


The CLI's release (`.github/workflows/cli-release.yml`, L4d) is apart from the library's: `dist plan` on PRs that touch `crates/laminapdf-cli`, `packages/cli`, `tools/cli-release` or the dist config; on `workflow_dispatch` (`dry-run` true; false is refused) and `laminapdf-cli-v*` tags, `cargo xtask cli-dist` and `dist build` for all eight targets, each on a GitHub-hosted runner of its own system and CPU (L4g: `macos-15`, `macos-15-intel`, `ubuntu-24.04-arm`, `ubuntu-24.04`, `windows-11-arm`, `windows-2025`; Windows in Git Bash), each archive extracted and run, the npm tarballs installed and run where npm installs them (`tools/cli-release/install-test.sh`; not the musl packages, whose static binaries are checked and run), the Homebrew formula installed from the local archive through a throwaway tap on macOS; then `global`: the formula, `sha256.sum`, the nine npm packages packed with `publish.json` (`tools/cli-release/generate.ts --pack`: the version, its dist-tag, platform packages before the wrapper) and a CycloneDX SBOM; then, only on a tag push while the variable `LAMINA_PDF_PUBLISH_CLI` is `true`, after every build passed, in the `release` environment: `publish` (the GitHub release with build-provenance attestations, which GitHub makes only for a public repository), `publish-npm` (npm trusted publishing from `ubuntu-latest`, versions already on npm skipped, a package not yet on npm refused with the owner's first-publish step) and `publish-homebrew` (the formula written to `laudebugs/homebrew-tap` through the contents API with a release-bot token for that repository alone); `tools/xtask/src/workflows.rs` tests the gates, the OIDC jobs, the only secrets (the release bot's, in `publish-homebrew`) and the build matrix against dist's targets. The owner's one-time setup is in `tools/release/README.md`.

The desktop app's release (`.github/workflows/desktop-release.yml`, D6b; ADR 0014; runbook `docs/guidelines/desktop-release.md` §6) builds six targets with the Tauri CLI on runners of their own OS and CPU (`.github/actions/desktop-build`): nightlies from the schedule in `desktop-nightly` (`X.Y.Z-nightly.YYYYMMDD.N`, NSIS only on Windows, skipped when nothing the app is built from changed in 24 hours), staging trials from a dispatch and beta releases from `desktop-v*` tags in `desktop-release` (the owner approves; Linux packages GPG-signed); pull requests that change the workflow dry-run every target with no environment or secret. macOS release builds are signed with the owner's Developer ID and the hardened runtime, notarised and stapled, `.dmg` included (D6c: the build action's keychain, `cargo xtask desktop-sidecar` signing PDFium with `APPLE_SIGNING_IDENTITY`, `tauri.developer-id.conf.json`; nightlies and dry runs ad hoc without the hardened runtime, and every macOS build has its bundled engine draw a page). Windows builds from `desktop-release` are Authenticode-signed through Azure Artifact Signing with GitHub's OIDC token (D6d: `apps/desktop/scripts/sign-windows.ps1`, every PE file in both installers checked). With both in `SIGNED_PLATFORMS`, tags publish. Each build checks the 16 MB budget and writes SBOMs; `attest` attests every file; the publish job (`.github/actions/desktop-publish`) uploads to R2 and writes the channel's manifest with the manifest tool's `upload`, `publish` and `verify`. `tools/xtask/src/workflows/desktop_release.rs` checks that no `desktop-nightly` job names an `APPLE_*`, `AZURE_*` or `LINUX_SIGNING_*` secret.

Daily releases: `release-train.yml` runs after a full successful nightly on `main`. It prepares and atomically pushes a version branch and tag with the release bot. The release lane deploys production docs after publishing and registry checks, then opens the version PR with auto-merge. `RELEASE_TRAIN=off` stops future trains. The web reader releases on its own: `web-release-train.yml`, after the same nightly, tags `web-v<next>` when what the reader ships changed since its last tag (`cargo xtask web next-release`; `WEB_RELEASE_TRAIN=off` stops it), and the tag deploys it. The CLI releases with every daily release: `cli-release-train.yml`, after the release lane succeeds for a `v<version>` tag push, has the release bot tag `laminapdf-cli-v<version>` on the same commit, and the tag runs `cli-release.yml`. `CLI_RELEASE_TRAIN=off` stops it. Workflow installation, bot setup and recovery: [`tools/release/README.md`](../../tools/release/README.md).
