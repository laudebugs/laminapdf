# laminapdf-content

Read what a PDF page draws, operator by operator, with the graphics and text state in effect, and add content to a page without touching what it already draws. The interpreter is tolerant of malformed content streams and reports each operator to a visitor you write. Most programs use it through [`laminapdf`](../laminapdf/README.md), which wraps the core crates in one API.

Content-stream interpretation ([ADR 0023](../../docs/decisions/0023-content-stream-reading.md)): what a page draws, operator by operator, with the graphics and text state in effect. Below `laminapdf-text` (B9b, text extraction), which is its first consumer; the editor's append (E2) and editing (E7, ADR 0022) rounds extend it. Part of Lamina PDF's pure core: bytes in, bytes out.

- `ContentIter`: a tolerant tokenizer over decoded content bytes (ISO 32000-2 §7.8.2), over `laminapdf-syntax`'s lexer and parser. Yields `Lexed::Op(Op)` (an `Operator`, one variant per Annex A operator plus `Unknown`, with the operands read since the previous one and its byte offset; `BI … ID … EI` is read whole as one `Op` with its `InlineImage`) and `Lexed::Issue` for skipped bytes. `Operator::signature()` and `Signature::check` give each operator's operands.
- `interpret_page(doc, page, visitor)` / `interpret_content(doc, bytes, resources, visitor)`: runs content against a `GraphicsState` (CTM, line style, colours, an `ExtGState` subset) and its `TextState`, the text matrices, the `q`/`Q` stack, resources (a form without `/Resources` uses its parent's; named colour spaces give their initial colour), Form XObjects (recursively, bounded, cycle-checked by object identity) and marked content, and reports to a `Visitor`: `operator`, `show_text` (returns the `TextAdvance` the glyphs moved; glyph widths are `laminapdf-text`'s), `path_segment` (with its CTM), `paint_path`, `set_graphics_state`, `paint_shading`, `image`, `begin_marked` / `end_marked` / `marked_point`, `enter_xobject` / `leave_xobject`, `warning`. Returns a `Summary`.
- Tolerance (ADR 0023 §3): unknown operators skipped (silently inside `BX`/`EX`), bad operands skipped and extra ones ignored, unbalanced `q`/`Q`, `BT`/`ET` and `BMC`/`EMC` repaired per stream, missing resources skip their operator, inline-image ends found by `/L`, computed size or the pdf.js heuristic. Each repair is a `Warning` (`content-unknown-operator`, `content-bad-operands`, `content-unbalanced-q`, `content-unbalanced-bt`, `content-unbalanced-marked`, `content-syntax`, `content-resource-missing`, `inline-image-unterminated`, `xobject-cycle`, `content-path-unpainted`) reported to the visitor and recorded on the document; strict mode makes it `Error::Strict`.
- The append API (`src/write/`, E2e): `PageContentWriter::new(cos_mut, &page)` writes to one page through a `CosMut`, so the caller's transaction undoes it.
  - `wrap_existing()` puts the page's content between a stream holding `q` and one holding `Q` once plus once per `q` the content leaves open. Before the `Q`s it writes an `EMC` for each marked-content sequence and an `ET` for a text object the content leaves open. An already wrapped page is left alone (`Wrapped::Already`). Content ending inside a string, array, dictionary or inline image is refused with `invalid-structure`; a wrap that would pass `max_nesting_depth`, or streams past `max_decoded_total` together, fail with `limit-exceeded`.
  - The only change to existing content is turning each `Q` read at depth 0 into `q Q`, a save and restore that changes nothing, in a new copy of its stream. A blank would also neutralise it, but not after an inline image: the `EI` heuristic ends an image only where an operator or operand follows.
  - `prepend` (inside the wrap on a wrapped page) and `append` add Flate-compressed streams ending in a newline. They refuse content that restores a state it didn't save, leaves one open or ends inside a token.
  - `add_xobject`, `add_extgstate` and `add_font` register a resource under a name (`Fm1`, `Gs1`, `Ft1`, …) that neither the page's resources nor its content uses. The name goes in the page's own copy of its resources, so a dictionary other pages share or inherit never changes.
  - `scan_balance(streams, limits)` is the token scan behind the wrap: the depth left open, every `Q` read at depth 0 (`StreamOffset`s), the deepest nesting, open text objects and marked content, and whether the page is already wrapped.
- Limits (ADR 0023 §4, all hard): `max_content_operators` (every operator of one call, forms counted each time they are drawn), `max_xobject_depth`, `max_nesting_depth` (saved states per stream), `max_decoded_total` (bytes interpreted).

Tests: unit tests in `src/{operator,lexer,state}.rs`; `tests/operators.rs` (every Annex A operator and its operands, malformed and unknown operators, inline images), `state.rs` (CTM, text matrices and text state against hand-computed §8.3.4/§9.4 values), `xobjects.rs` (forms, depth 32/33, cycles, images), `marked.rs`, `limits.rs` (each limit at and past its value, strict mode), `append.rs` (the append API over `fixtures/content/append/`: what each wrap writes and neutralises, resource names, shared streams and dictionaries, rollback, the paths the interpreter sees before and after), `corpus.rs` (every fixture page against pdf.js's operator list in `fixtures/corpus/pdfjs-operators.json`) and `regressions.rs` (the `content` fuzz target's saved crashes). The `content` fuzz target's entry point is `tests/common/fuzz_entry.rs`, `content_append_scan`'s `tests/common/append_fuzz_entry.rs`. The render diffs (a wrapped page renders the same; a square appended to every page of the corpus changes only its pixels) are `laminapdf-render-pdfium`'s `tests/append.rs`, with hayro in every run and PDFium in `cargo xtask render-golden`.

```sh
cargo test -p laminapdf-content
cargo xtask fuzz content --time 600
cargo +nightly fuzz run content_append_scan --fuzz-dir fuzz -- -max_total_time=600
```
